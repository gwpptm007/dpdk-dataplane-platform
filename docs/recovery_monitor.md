# 独立接口监护与会话证据

`dppd-monitor` 在业务进程启动前观察预先创建的持久 TAP。业务进程被强制结束后，
监护仍独立运行；接口删除、改名、身份冲突或事件丢失会使会话失效，并保存原因。
业务可通过 `--recovery-monitor` 显式绑定会话，进行启动和安装前后的新鲜回复检查，
详见 [业务与监护握手](recovery_monitor_handshake.md)。会话尚未作为清理计划的执行依据。

## 启动与查询

先准备属于当前测试或部署的持久 TAP，以及已存在的私有存储目录。监护不会创建、
配置或删除接口，`PORT:IFNAME` 必须与后续业务进程的端口映射一致：

```sh
sudo ./build/dppd-monitor run /var/lib/dppd/hardware.recovery \
  /var/lib/dppd/rules.state /var/lib/dppd/monitor-session-001 \
  0:dppdtap0 1:dppdtap1
```

工具前台运行。看到 `monitor ready` 后，在另一个终端启动业务进程，使用相同的
`--recovery-path`、`--state-path` 和 TAP 映射。若需要原生规则标识，仍按
[TAP 原生标识](tap_owner_cookie.md) 启用补丁与 `--tap-owner-cookie`。
监护工具不负责启动业务。业务配置 `--recovery-monitor SESSION_PATH` 后会自动核对完整
端口映射及会话起点；只启动监护而未配置该选项的旧 v5 业务不受此握手约束。

```sh
sudo ./build/dppd-monitor show /var/lib/dppd/monitor-session-001
```

`run` 开始时短暂持有恢复文件的排他锁，拒绝正在被业务使用的文件或尚有待确认活动的
记录。干净恢复文件不存在时会按现有规则创建，干净旧格式允许升级；已有待确认文件
保持原样。随后订阅事件、读取 TAP 身份、检查启动窗口、持久保存会话，最后释放恢复锁。
业务快照不被读取或修改。会话文件必须不存在，不能覆盖已有会话来隐藏中断历史。

就绪后，监护保留原恢复文件的描述符以防 inode 被回收复用，但不继续持有其安装锁。
每轮检查原路径是否仍指向该私有、单链接文件，正常业务写入恢复记录不影响监护。
这一检查绑定文件实例，不验证恢复文件每次修订的内容，也不能发现所有短暂路径替换。

## 如何解释结果

示例首行：

```text
monitor state=active sequence=1 reason=none error=0 writer-lock=held freshness=unverified executable=no
```

后续行列出随机会话编号、记录的 PID、单调时钟时间、恢复文件路径及设备号/inode、
启动时的 revision/attempt 编号，以及各端口的名称、索引、系统启动标识与网络命名空间。
时间值仅用于同一系统启动内比较，不是日历时间。

| 查询状态 | 含义 |
| --- | --- |
| `active` | 文件记录为活动状态，查询时排他文件锁被占用；不能据此证明监护仍在处理事件 |
| `interrupted` | 文件仍为活动状态，但已没有写入者占锁；显示 `writer-missing` 和 `-EOWNERDEAD` |
| `invalid` | 已持久保存观察失效及原始错误，不能恢复成同一个活动会话 |
| `stopped` | 收到 SIGINT/SIGTERM 后保存停止终态，之后不再观察 |

`show` 全程只读，识别进程被 SIGKILL 后的中断时不会改写旧文件。文件锁比旧 PID 更适合
识别写入者是否已经退出，但暂停的进程仍持有锁，所以所有查询明确输出
`freshness=unverified executable=no`。这些输出也不是心跳或清理许可。

成功读取上述任一状态时，`show` 返回 0；文件损坏、权限不符、符号链接、硬链接或读取
失败时返回非零。终态写入与查询并发时，查询可能因读到不完整编码而拒绝，可稍后重查。
`run` 正常停止返回 0，观察失效或写盘故障返回非零。

## 观察范围与失效原因

生命周期模式允许同名同索引的普通链路状态通知，以及正常 TC 创建、修改和删除。
这样业务启动、链路状态切换和规则安装不会被当作接口已重建。
它仍接收并检查 TC 消息边界，丢包或损坏不能被忽略。

| 原因 | 触发条件 |
| --- | --- |
| `interface-changed` | 相关接口被删除、改名，或名称/索引只匹配其中一项 |
| `observer-lost` | 接收丢包、截断、未知消息、事件风暴达到上限、socket 错误等 |
| `recovery-record-replaced` | 检查发现原路径消失、文件被替换、多链接或权限被放宽 |
| `stop-requested` | 正常信号停止，不再继续覆盖后续事件 |
| `writer-missing` | 只读查询推导出的中断，磁盘仍保留此前的活动记录 |

接口删除后即使恢复同一个名称与索引，先前的删除通知也不会被抹掉。会话进入终态后
不能重新激活，业务活动尚未确认清理时也不能补开新会话。正常业务 TC 更新被允许，
因此该会话不证明规则内容从未变化；离线计划仍使用更严格的
[查询窗口事件监视](recovery_observation_window.md)。

## 会话文件 v1

会话证据与恢复记录分开保存，管理协议和外部确认清理流程保持不变。业务显式握手时
恢复记录升级为 v6 保存会话编号，普通模式仍为 v5；会话文件本身仍使用本节的 v1 格式。
新文件固定 **5760 字节**，显式小端编码，权限 `0600`，最多 16 个端口。

| 字节范围 | 内容 |
| --- | --- |
| 0–31 | `DPPMON1\0`、格式版本 1、长度、状态序号、端口数、CRC32 |
| 32–63 | 16 字节随机会话编号、状态、原因、负 errno、记录的 PID |
| 64–111 | 恢复文件设备号/inode、起始 revision/attempt、开始和更新时间 |
| 112–127 | 保留零字节 |
| 128–4223 | 4096 字节恢复文件绝对路径，含结束零字节 |
| 4224–5759 | 16 个 96 字节端口槽位 |

每个端口槽位依次保存端口编号、保留位、接口索引、16 字节接口名、40 字节 boot ID、
网络命名空间设备号/inode，剩余字节为零。未使用槽位和字符串尾部也必须为零。
CRC 字段按零计算校验和；CRC 只发现损坏，不提供身份认证。

序号 1 表示初始活动状态，序号 2 表示唯一一次终态写入。初始文件与目录都同步成功后
才打印就绪；终态同步完成后才更新内存状态。写入或同步失败会锁存故障并退出，不重试
把会话恢复为可信。根据失败位置，磁盘可能保留旧活动记录、终态或损坏数据，查询分别
显示中断、终态或拒绝读取；任何一种都不能作为自动删除依据。

## 当前边界与下一步

独立进程、持久失效证据以及可选的 [业务握手与安装检查](recovery_monitor_handshake.md)
已完成。离线 `show` 仍不主动握手，文件及被占用的锁仍不能证明当前活性。

下一步建立受控写入者和恢复交接，再把证据接入清理计划。监护允许正常 TC 写入，
尚未约束其他写入者，也没有实现检查到删除之间的隔离。事件订阅本身不能补证启动前
的历史，不能单独把当前记录解释成连续历史的完整证明；实际跨进程删除仍未实现。

## 验证

2026-10-11，系统 DPDK 21.11.9 和原生标识补丁构建均完成 `-Werror` 编译和
**33/33 单元测试**。监护证据、事件监视、清理计划、TAP 查询四项通过
AddressSanitizer/UBSan，覆盖真实进程死亡后的文件锁释放、状态不可逆、编码损坏、
保留字段、重复身份、随机源失败、部分写入、文件/目录同步失败和文件替换。

真实集成测试仅创建并按索引核对后删除自己的持久 TAP：

```sh
sudo python3 tests/integration/recovery_monitor.py --build-dir build
sudo python3 tests/integration/recovery_monitor.py --build-dir build-native --native
```

两种构建各验证九个场景：业务先退出、监护先退出、双方退出、业务退出后正常停止监护、
单独正常停止、暂停期间同名同索引重建、改名、恢复文件替换和事件丢失。每个场景核对
恢复文件与业务快照未被监护改变；业务活动存在时补开会话被拒绝，旧会话文件不能覆盖。
事件丢失仅注入独立测试入口，正式程序没有故障开关。

既有八个查询窗口场景、原生标识与内容核验、旧格式/锁/版本的只读检查，以及两种
构建下的六个真实创建窗口一并回归通过。Linux 验证源码与工作区的 138 个源码、头文件、
Python、Meson 和补丁文件按忽略换行差异的 SHA-256 核对一致。
