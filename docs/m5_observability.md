# M5 运行观测、线程心跳与 NUMA 布局

本功能接入正式 `--flow-state` daemon。管理线程发布纯数据副本，DPDK telemetry 查询线程不进入
配置仓库、持久化文件或 PMD。现有本地 `health`、`ready` 和 `stats` 语义继续保留。

## 结构化日志

新增事件以单行 JSON 写入标准错误，`schema=1`、`component=dppd`。事件包括启动、就绪、隔离、
退出、线程超时、规则副本失败和周期统计。`monotonic_ms` 是本次启动中的单调时钟，不能作为跨主机
UTC 时间比较；部署日志采集器可以附加接收时间。事件只写固定字段，不记录认证材料或用户文件内容。

`worker_layout` 记录队列、lcore、socket 和心跳超时。`stats` 按现有 `--stats-ms` 周期记录接收、
发送和规则丢弃累计值。原有 EAL/PMD 文本日志仍然存在，采集器应按 JSON `schema` 区分新事件，
不能假定整个进程输出都是 JSON。

新 JSON 事件采用尽力交付，不承诺持久审计。每条记录长度有界，管道、终端和 socket 的写入不会等待
接收方腾出空间，满管道、断开连接或其他写入错误会增加 `/dppd/managed/status` 的 `log_dropped`
累计值，线程超时退出不受这些接收方背压阻塞。实现不改变父进程共享的 stderr 文件状态标志，也不
全局屏蔽 `SIGPIPE`。日志缺失不改变策略持久回执；需要审计留存时应另行配置可靠的外部采集器。

普通文件仍使用内核文件写入，磁盘 I/O 卡死需要外部监护。上述保证只覆盖新增 JSON 事件，原有
stdout 统计、错误文本和 EAL/PMD 日志仍可能同步输出，不能据此宣称整个进程在所有日志介质故障下
都能有界退出。

## Managed telemetry

启用 EAL telemetry 后，在本实例的 `dpdk_telemetry.v2` socket 查询：

| 命令 | 参数 | 内容 |
| --- | --- | --- |
| `/dppd/managed/status` | 无 | 正式 health 副本、配置/持久修订号、任务、AGE、隔离和副本错误 |
| `/dppd/managed/stats` | 可选 `port,queue` | 端口和队列维度的全部软件报文计数，`65535` 表示全部 |
| `/dppd/managed/rule` | `rule_id` | 精确规则版本、模板、队列和 COUNT 样本 |
| `/dppd/managed/worker` | `queue_id` | 状态、心跳时间、心跳年龄、超时阈值和实际 lcore/socket |

格式沿用 DPDK telemetry 的逗号分隔参数。非法参数、未知 ID 和当前不可用的查询返回 `null`，
不能把 `null` 当作零计数。状态有 `sampled_ms`，规则计数另有 `count_sampled_ms`。

规则元数据在配置修订变化后发布。计数采用按需采样：首次查询登记意愿并返回 `null`，管理线程每轮
最多处理 16 个采样请求，后续查询返回最近样本并登记刷新。请求按轮转顺序处理，避免持续查询低编号
规则饿死其他编号。该设计避免为了无人读取的指标，每秒对大规模软件规则表做平方级扫描。
客户端可以重试首次查询，并根据采样时间判断数据新鲜程度；这些指标不是逐包一致性快照。

私有 COUNT 使用 `shared=0`；共享 COUNT 使用 `shared=1` 并给出对象 ID 与代次，`hits/bytes` 是该
共享对象的总值，不能将各引用规则显示的值相加。没有 COUNT 的规则显示 `count_available=0`。
发生存储 dirty 或恢复隔离时，规则副本明确失效，修复后重新发布，旧样本不会冒充当前配置。

## 心跳与失败退出

`--worker-timeout-ms` 配置心跳阈值，默认 5000 毫秒，0 显式禁用，启用时允许 100～600000 毫秒。
该选项只在 `--flow-state` 正式入口启用；旧入口自动关闭监护，显式传入正数会被拒绝，避免进入旧有
无限等待的清理路径。
worker 每轮检查廉价周期计时器，约每 10 毫秒在完成收发扫描和 QSBR 安全点后发布单调时间。
即使没有流量也会发布心跳，因此空闲不能掩盖卡死。

启动请求发送前初始化心跳，重新启动时重置基线。正常停止、配置隔离期间的暂停和设备 I/O 门禁不会
误报卡死。真正超时后，正式入口记录 `worker_timeout` 并非零 `_Exit`，不会无限等待卡死线程，
也不会释放仍被该线程借用的内存。该路径不会输出正常清理完成事件。
停止和隔离暂停虽然不再判断运行期心跳，等待线程退出本身仍使用相同超时上限；卡死线程不能通过
恰好收到停止请求而绕过限时退出。部分线程启动失败后，也保留已经启动的线程身份并等待或失败退出。

超时退出保留已可靠保存的配置。部署侧必须先确认旧 PID 已结束，再清理其遗留管理 socket 并启动新
实例。正式 managed 模式仅接受软件配置；本机制不能证明硬件流已从网卡消失，也不替代原生恢复监护。
整进程卡死仍需外部探针/进程监护，主线程自己的检查不能证明主线程也在运行。

## NUMA 自动布局

布局只从用户已启用的 EAL 非主核集合选择，既不扩大 CPU 集合，也不修改网卡绑定。
每个 worker 当前都处理所有配置端口的同编号队列，因此优先选择与最多已知端口同 socket 的核；
同分时均衡 socket，最后按 lcore 编号稳定选择。队列和 QSBR reader ID 保持从零连续编号。
网口或 CPU 的 socket 未知时保留未知语义，不伪装成已验证的本地节点。

mbuf 池和队列描述符继续沿用现有网口 socket 分配。跨 socket 的端口对仍可能产生远端访问，
虚拟机测试只能证明选核算法、EAL 约束与转发兼容，不能证明真实多 NUMA 网卡吞吐收益。

## 验收入口

单元测试验证纯拓扑选择、心跳边界、真实管理状态发布、端口/队列过滤、私有和共享计数范围、
字段错误传播、部分注册重试、dirty 副本失效及解绑后的访问拒绝。真实满管道、断开管道和 socket
测试在有闹钟上限的独立子进程中执行，核对日志丢弃计数及原描述符标志不变。

```sh
python3 tests/integration/m5_observability.py --build-dir build --report-dir build/m5-observability
```

集成入口使用正式 daemon/CLI 和独立 EAL 前缀，验证空闲心跳、真实 telemetry socket、规则精确
版本、JSON 生命周期/统计、选核约束。仅测试程序在真实 worker 首轮扫描后注入永久暂停，验证有界
失败退出、SIGTERM 遇到卡死线程时的限时等待，以及使用同一配置的精确重启恢复。测试程序不链接到
正式发布二进制。
