# 受控写入者登记与恢复交接检查

启用 `--recovery-monitor` 的业务现在必须向监护独占登记，才能持久绑定 v6 并开始安装。
恢复工具只有确认这次登记的业务已经退出、原恢复文件仍持锁、自己处于同一个网络
命名空间且会话仍有效，才能取得只读交接租约。本阶段还提供在租约内生成恢复计划的
命令，仍不修改或删除内核规则。

这里的“受控”指遵守项目入口的业务与恢复工具。管理员、其他 TC 程序及直接使用内核
接口的程序尚未被部署权限隔离，所以输出始终保留 `writer-exclusion=no executable=no`。

## 业务登记

启动方式沿用 [业务与监护握手](recovery_monitor_handshake.md)。业务核对完整 TAP 映射
和干净起点后，把已经持锁的恢复文件描述符通过 `SCM_RIGHTS` 交给监护核验。监护检查：

1. 连接凭据来自内核，有效用户相同
2. 描述符指向本会话绑定的私有、单链接普通文件，当前路径仍是原 inode
3. 独立打开确实受锁阻挡，传入的同一文件描述保持排他锁
4. 完整记录通过长度、CRC 与规范编码检查，revision 和逐次编号等于会话起点
5. 此会话从未登记过业务，内核支持取得该业务的 pidfd

登记成功后，监护持有业务 pidfd，关闭借用的文件描述符，业务再把会话编号同步写入
恢复记录 v6。以后每次安装和主循环检查都核对登记的业务身份。一个会话只接受一次
业务登记，即使同一进程重复请求也拒绝；登记回复丢失或随后绑定写盘失败，不能用旧
会话重试启动新业务。确认记录干净后，使用新会话重新启动。

pidfd 在内核进程退出后变为可读，暂停、socket 断开和 PID 数字仍存在都不是退出证明。
已经退出但尚未被父进程回收的业务可以满足退出条件。监护不会从磁盘里的 PID 数字
重建身份，也不会在崩溃后复用原会话；内核不支持 pidfd 时明确拒绝登记。
相关语义见 [Linux pidfd 手册](https://man7.org/linux/man-pages/man2/pidfd_open.2.html) 和
[Unix 描述符传递](https://man7.org/linux/man-pages/man7/unix.7.html)。

## 只读交接命令

业务意外退出、原监护仍正常运行时，先查询当前精确版本：

```sh
sudo ./build/dppd-recovery show /var/lib/dppd/hardware.recovery
sudo ./build/dppd-recovery handoff-check /var/lib/dppd/hardware.recovery \
  REVISION /var/lib/dppd/monitor-session-001
```

第二条中的 `REVISION` 替换成第一条实际返回的数字。成功时例如：

```text
handoff revision=5 business=exited lease=held scope=cooperative mode=read-only writer-exclusion=no executable=no
```

命令先取得恢复文件排他锁，再核对精确版本、v6 会话编号、恢复文件身份和活动监护。
监护必须仍持有最初登记的业务 pidfd，并确认其已经退出。恢复请求携带锁描述符和
精确 revision，监护重新解码文件后才回复，不能把客户端缓存的旧版本当成当前版本。
会话起点之后保存的每个恢复端口也必须属于监护的原端口集合，身份完全一致。
恢复进程的当前网络命名空间也必须与全部登记 TAP 一致。Linux 抽象 Unix socket 本身
按网络命名空间隔离，额外身份检查让拒绝发生在连接前并留下明确错误。

可以在同一租约中直接核对计划：

```sh
sudo ./build/dppd-recovery plan-monitored /var/lib/dppd/hardware.recovery \
  REVISION /var/lib/dppd/monitor-session-001
```

命令先取得租约，再运行原有的全端口只读计划；计划自身仍先订阅链路和 TC 事件，查询
结束后还要取得一次新鲜回复。完整且未观察到变化时，输出末尾增加：

```text
plan-evidence status=active revision=5 session=0123456789abcdef0123456789abcdef session-checked=yes lease=held history-covered=no writer-exclusion=no check-delete-exclusion=unavailable executable=no
```

没有此行表示监护检查或查询不完整。它只关联本次计划与一个活跃监护及合作式写入者
交接，**不证明监护启动前的 TC 历史，也不阻止有权限的其他程序写入**。因此单独保存
此计划不能授权之后的删除。

监护最多允许一个恢复租约，同时持有恢复连接、恢复工具 pidfd 和借用的锁描述符。
工具继续核对新鲜回复、租约连接和记录版本，打印结果后关闭租约并退出。正常退出或
工具被强制结束后，监护释放借用的描述符，下一个工具仍需重新完成全部检查。文件锁
与会话均未持久改写，租约不会跨监护重启保存。

恢复工具提前关闭自己的文件描述符时，监护仍保留同一把锁；若主动解锁，后续检查
失败并锁存。借用描述符只关闭，不显式 `LOCK_UN`，避免解除调用方仍需要的锁。
工具刚退出时，监护可能尚未处理关闭通知，紧接着的命令可以短暂得到 busy；监护暂停
期间也可能继续占锁，不能把它强行绕过后宣称交接成功。

## 拒绝与中断

- 业务仍存活或暂停时拒绝，即使恢复文件的锁被提前放开
- 未登记业务、旧会话、错误恢复文件、错误 revision 和不匹配的端口身份均拒绝
- 监护停止、死亡、暂停超时、会话文件替换或接口生命周期失效均不能取得有效租约
- 同时到来的第二个恢复工具拒绝，已有租约失效后必须新建客户端重新核验
- 请求缺少锁描述符，传入只读或其他文件，以及多余、截断的描述符均拒绝

IPC 每次往返仍共用 **1000 ms** 的单调时钟截止时间。普通信号打断等待后继续使用原
截止时间，持续信号不能延长预算。拒绝的请求关闭其连接，不返回成功回声，因此部分
权限拒绝会显示消息不完整；文件锁占用、错误版本、旧会话和超时在对应入口分别诊断。
错误在当前客户端内锁存，监护恢复后也不自动继续之前的操作。

## 格式与兼容

会话证据仍为 v1，恢复记录仍为 v6，本阶段不改变磁盘编码。业务登记和租约身份保存在
持续存活的监护进程中，监护死亡后缺失的内核凭据不能靠旧文件补造。

IPC 升级为 `DPPMIPC2`，固定 72 字节。前 64 字节沿用会话、随机数、设备号和 inode
字段，最后 8 字节保存本次精确 revision。请求类型分别为普通活性查询、业务登记、
业务身份检查、恢复租约获取和恢复租约检查。只有登记和获取租约携带一个锁描述符。
旧 IPC 版本明确拒绝，两端必须使用同一次构建，不会退回缺少写入者登记的检查。

## 验证与下一步

2026-10-11，系统 DPDK 21.11.9 和原生标识补丁构建各 **35/35 单测**通过，相关六项
AddressSanitizer/UBSan 检查通过。真实进程测试覆盖业务活着但已放锁、暂停、僵尸状态、
独占登记、身份错配、租约争抢、借用锁的生命周期、主动解锁、工具被杀和失败锁存。

```sh
sudo python3 tests/integration/monitor_handoff.py --build-dir build
sudo python3 tests/integration/monitor_handoff.py --build-dir build-native --native
```

每种构建十个真实 TAP 场景：业务存活、错误会话、监护暂停、被杀、正常停止、会话替换、
接口改名、恢复争抢、交接中断，以及查询完成后监护退出。最后一个场景确认没有输出
计划有效性证明。所有成功和拒绝路径均核对原残留规则、恢复文件与业务快照未变，
测试只创建和删除自己的持久 TAP。既有握手及创建窗口同时回归。

恢复租约已要求同一网络命名空间，`plan-monitored` 也将全端口只读查询放在租约内。
下一步限制命名空间内有能力写 TC 的进程，并把历史连续性证据与后续精确删除放入一个
持续持有租约的操作。当前两条计划命令仍都输出 `executable=no`。
