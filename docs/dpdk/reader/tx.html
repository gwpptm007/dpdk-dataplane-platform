一个包交给网卡以后

TX 描述符、发送完成与 mbuf 回收

rte_eth_tx_burst() 返回 3，应用就不能再碰那 3 个包。 可网卡也许还没读完它们，内存池也还没拿回空间。沿着这些不同的时刻，理解发送为什么必须是一条完整的责任链。

承接 RX 与 mbuf 样章提交 → 完成 → 回收部分发送与资源压力

01 函数返回了，事情为什么还没做完

上一章里，CPU 从接收路径拿到的是已经装有数据的 mbuf。现在它完成规则匹配或报文改写，要把这个包送往另一个端口。 最直观的实现是一直等待：等网卡读完所有字节、把它们发出，再让发送函数返回。这样很容易判断何时释放内存，却把 CPU 与较慢的设备进度绑在一起。

常见的物理网卡发送路径采用异步交接：CPU 先把“数据在哪里、该读多少、怎样处理”的工作交给设备，随后继续处理其他包。 设备在自己的时间线上取数据并推进发送。应用得到的返回值首先回答有多少个包已被这条发送路径接受，并不回答远端是否已经收到。

需要分开的三个边界
边界可以得出什么结论还不能得出什么结论
TX burst 接受已接受前缀的后续管理责任交给发送路径网卡已经读完、mbuf 已回池、对端已经收到
设备完成依据成立驱动可以按设备协议推进相应资源的回收另一端应用处理成功，或者软件回收代码已经执行
软件回收执行驱动释放引用、更新队列可用资源所有共享引用都已消失，或每个对象立即进入其他核心可用的公共池

可以借用“把材料交给加工设备”的类比，但不能把设备完成当作快递签收。 网卡报告的是本地发送协议中的进度；对端可能因链路错误、过滤、拥塞或自身资源不足而丢弃。 如果业务要知道对方是否收到，需要上层协议的确认机制。即便收到 TCP ACK，也只是相应协议语义下的确认，不等于对方业务已经把结果持久化。

这里最重要的纪律

在普通“把当前引用交给 TX”的用法中，已接受包不再由调用者访问或释放。 不能用“函数还没退出”“设备应该没那么快”来证明旧指针仍安全。 若刻意保留另一份引用，必须另行设计引用和只读共享协议，不能靠复制 C 指针获得第二份所有权。

应用与驱动约定见 固定版本的 ethdev TX burst 接口。 下面会把这份通用契约与一个具体驱动实现分开，避免把某种硬件的字段名字当成全部 DPDK 的统一格式。

02 CPU 交出去的不是一根网卡能理解的 C 指针

应用有 struct rte_mbuf *m，但网卡不需要按 C 结构体布局遍历 m。 PMD，即应用线程执行的设备收发驱动，会把软件表达翻译成设备规定的 TX 描述符。 描述符是设备工作单；它通常引用原有数据区，而不是把整包内容复制到描述符里面。

从 mbuf 到设备工作单，中间保留了两类信息
信息为什么需要谁主要使用
数据 IOVA 与段长设备要知道从哪里读、读多少字节；IOVA 是设备侧 DMA 地址NIC，也就是网卡
包结束与处理命令多个数据段怎样组成一包，是否需要特定卸载处理NIC
mbuf 软件记录设备任务结束后，驱动要找回对应对象和它所属的池PMD
完成追踪与环索引区分仍在使用、可以回收和可以重新提交的槽位设备与 PMD 按各自协议协作

DMA 是设备直接访问内存。RX 典型地让设备向主机数据区写入，TX 则让设备从数据区读取。 CPU 虚拟地址与设备 IOVA 需要正确映射到同一份存储；把 m 的整数值写给网卡，并不能代替这套映射。 在后面的 ixgbe 简单路径中，驱动从 mbuf 取得数据 IOVA 和本段长度，写入描述符，同时把 mbuf 指针保存在软件配套数组里。

为什么多段包会改变队列容量的含义

假设一个包由三段组成：第一段 64 字节，第二段 1024 字节，第三段 200 字节。 三块内存不必连续，但设备可以按散布的地址收集数据，把它们组织成同一个包。 在典型 ixgbe 多段路径里，这会消耗多个数据描述符，最后一段使用 EOP，即 End Of Packet、包结束标志。

所以“空了 10 个描述符”不能普遍换算成“还能发 10 个包”。 一些卸载还要用 context descriptor，也就是提供校验和、分段等处理参数的上下文描述符。 它占队列位置，但不对应另一份待发包字节。应用 API 返回的是包数，驱动计算空间时处理的却可能是描述符数，两个计量单位要分开。

写好内存以后，为什么还要通知设备

描述符在内存里出现，不等于设备已经获准消费它。 ixgbe 使用 TDT，即发送描述符尾寄存器，表示新的提交边界；驱动推进它，类似向设备按下“有新工作”的门铃。 在本章的路径里，描述符填写完成后先执行写屏障，再更新 TDT，保证发布顺序符合该平台和设备的约定。

写屏障不是“等待设备把包发完”，也不是“把所有缓存清空”。它处理的是内存访问的可见顺序。 如果设备先看见新的提交边界、却还没看见对应的新地址和长度，就可能消费旧工作单。 把“准备内容”和“发布内容”分成两个动作，是理解许多高性能队列的共同入口。

本节设备字段的具体定义和写入顺序可对照 tx1、tx4 与 ixgbe_tx_fill_hw_ring。 程序复制的是少量指针和描述符字段；设备随后仍要读取真正的报文字节，减少 CPU 全包复制并不让这段内存带宽消耗消失。

03 跟着一个包走到回收，而不是停在函数返回

先限定普通单段 mbuf、有效数据且不请求 TX 卸载的发送场景。 具体顺序选用 DPDK v24.11 的 ixgbe_xmit_pkts_simple()，它进入 tx_xmit_pkts()， 并通过 ixgbe_tx_free_bufs() 回收满足条件的一组旧对象。

这是一条用于讲解的简单标量路径，即按普通 CPU 指令处理对象；实际设备可能选择向量路径或支持更多卸载的完整路径。 它们可以共享应用侧契约，却不必在相同时间释放同一批对象。图中跟踪一组 32 个包，明确列出阈值和资源假设；这不表示应用每次必须发送 32 个包。

04 设备完成了，为什么池里还没多出对象

“完成”首先是一种依据。要让对象回到可复用资源中，还需要 CPU 执行回收代码，释放引用并更新软件状态。 如果驱动每发一个包就马上读取一个完成结果、回收一个对象，会增加设备写回、CPU 检查和访问池的次数。 因此所选路径把多个完成与回收动作合并处理，让额外工作被一批包分摊。

RS 与 DD：请求报告，与观察到报告

RS 是 Report Status，意思是让设备为选定描述符报告完成；DD 是 Descriptor Done，是驱动检查的完成结果。 这条简单路径并不要求每个描述符都独立报告。它按 tx_rs_thresh 划分报告边界， 回收函数检查 tx_next_dd 所指边界的 DD，再按该设备的顺序保证处理这一组对象。

这并不意味着“把任意一个 DD 看成前面所有包都完成”。组的范围、提交顺序和硬件保证必须配套。 驱动保存这些关系，应用通常只应使用设备接口，而不是从外面猜一个描述符位来决定能否释放。

两个阈值解决的是不同问题

不要把报告间隔与软件扫描条件混成一个开关
参数在所选路径里控制什么不能怎样理解
tx_rs_thresh设置完成报告边界和按组追踪回收的粒度不是每次 TX burst 必须提交的包数
tx_free_thresh空闲描述符低于此值时，在发送路径中尝试回收不是“已经发送了这么多包就必须回收”，也不是后台定时器

用一个有意省略硬件细节的例子理解：假设一组报告覆盖 32 个单段对象。 设备完成边界后，软件一次处理这一组，平均检查成本可能比逐个查询更低；代价是较早完成的对象可能继续被驱动暂存。 32 在这里只用于解释，真实配置还受到驱动对环大小、阈值、路径选择的约束，不能照抄为任意 PMD 的推荐值。

甚至“描述符重新可用”和“mbuf 引用已经释放”也不能在全部驱动中等同。 本章的简单路径在回收组里调用预释放并向池归还可释放对象；ixgbe 完整路径的清理与槽位重用流程不同，可能先推进描述符空闲计数，再在后续位置释放旧对象。 源码走读时要沿同一条发送回调追到底，不要从简单路径摘一个函数、再用完整路径的另一半拼成不存在的流程。

只发送几包后停下来，为什么看起来像“内存泄漏”？

如果没有后续发送调用触发回收，或者尾部未达到所选路径能观察的完整报告组，驱动可能继续持有那批对象。 因而“发完之后池里少几个对象”不足以单独证明泄漏。应先确认持有者、完成依据与清理流程， 再区分正常暂存、无法推进的状态以及真正丢失的引用。

rte_eth_tx_done_cleanup() 是请求驱动归还已经不再使用的发送对象的接口，不是强制完成未结束的 DMA。 返回 0 可能表示当前没有可回收对象；驱动或具体路径也可以返回 -ENOTSUP。 所选 ixgbe 简单实现仍按组回收，因此把 free_cnt 设为 0 也不能承诺立即清空不足一组的尾部。

应用自行积攒但还没提交的发送缓冲又是另一层，需要相应的 flush 操作。 不要把一次零包 TX 调用当作所有驱动通用的“发完并回收全部”命令，也不能直接 free 已交出去的包来让池计数好看。

“池可用量”到底统计共享池，还是也统计本核缓存？

先认清使用的接口。rte_mempool_avail_count() 会把池内置的各 lcore 缓存也计入可用量， 不统计应用另行管理的 user-owned cache。因此对象进入内置本核缓存，本身不能解释这个接口统计的可用总量为何减少。 但另一个核心不能直接从你的本核缓存取对象，所以“全池还有空闲”和“当前核心能否分配成功”仍然可能不同。

这里的 lcore 是 EAL 管理的逻辑执行核。这个全池计数适合诊断，不应放进每包热路径； 并发收发时也不要把多处采样当成同一瞬间的守恒快照。具体计数范围见 mempool 的 avail_count 与 get 接口说明。

具体回收代码见 ixgbe_tx_free_bufs、 ixgbe_tx_done_cleanup_simple； 通用请求语义见 ethdev 的 tx_done_cleanup 文档。

05 发送不足时，先分清谁还持有剩下的包

给 TX 一个数组 [A, B, C, D, E]，返回 3，含义是前缀 [A, B, C] 已交接， 尾部 [D, E] 仍由调用者负责。它不是从五个包里随意挑了三个，也不是“这五个都已排队，只完成了三个”。 忘记处理尾部会遗失引用；把整个数组都释放，则会把驱动仍可能使用的前缀提前归还。

自己操作一次：五个包，分别由谁负责

这是独立的 API 所有权练习：应用持有 A～E，池里另有 3 个空闲对象。改变返回值后提交，页面按本项目策略立即释放未接受尾部。 随后分别触发“设备完成”和“驱动回收”，观察池余量何时增加。

重试能吸收短时阻塞，不能创造长期发送能力

若设备很快完成一批旧任务，稍后重试尾部可能成功。但无限循环重试会把 worker 卡在出口： 它不再服务其他入口，不再及时处理停止或设备事件，持有的 mbuf 也迟迟不归还。 可靠的重试设计需要次数或时间上限、等待队列容量、停止条件，以及最终放弃时的释放责任。

用资源守恒推导，假设输入长期为每秒 100 万包，出口实际长期只能消化 80 万包，且没有丢弃或流控降低输入。 积压每秒增加 20 万包。多准备 20 万个单段对象，理想化地只增加约 1 秒缓冲时间； 它没有改变两端速率差。这是假设计算，不是本项目吞吐测试，更没有计入每包可能占用多个 mbuf 的情况。

如果 RX 与 TX 共用一个池，出口暂存越多，入口能申请到的替补就越少。 因此入口分配失败的根因可能在出口回收或业务排队。完整的资源路径应画成 池 → RX → 应用 → TX → 池，任何一段长期停留，都可能影响下一轮接收。

准备发送、校验和卸载与 TSO 怎样改变这个模型

rte_eth_tx_prepare() 用于发送前的检查或必要调整；它可能检查段数、卸载参数，并修改需要准备的校验和字段。 因此输入数据必须安全可写。返回值表示前面多少个包已准备好，不表示这些包已提交，准备后仍要调用 TX burst。 准备过程不转移这些包的所有权，调用者仍负责它们。 遇到第一个不合要求的包时，准备过程停止，后面的包不继续准备；调用者需要分别处理已准备前缀与剩余部分。 驱动未实现 prepare 时，还可能直接原样返回全部数量，不能把这个结果当作所有设备要求都已验证。

校验和卸载把某些字段的计算交给设备，应用仍要提供正确的头长和标志。 TSO，即 TCP Segmentation Offload、TCP 分段卸载，会让一个软件大包在设备侧变成多个线上报文。 因而一个 TX 返回计数与对端观察到的帧数不一定一一对应。使用这些能力前，要同时核对设备能力、端口与队列配置、mbuf 元数据以及报文内容。

本章的简单路径特意不把这些扩展混进主时序。它们说明的是同一个原则： 应用要交付的不只是字节，还有驱动能够正确解释的描述；更快的硬件路径也需要更精确的输入契约。 可对照 tx_prepare 接口与 mbuf 卸载元数据说明继续追踪。

06 本项目的发送函数为什么这样写

下面固定到项目提交 c793dbd。这里的 worker 不自己构造 ixgbe 描述符，也没有把某张网卡的回收阈值硬编码进业务处理。 它通过 ethdev 接口提交包，把设备差异留给实际 PMD。前面研究驱动，是为了理解接口背后的约束，而不是把驱动实现复制进 worker。

设备配置在能力允许时启用 RTE_ETH_TX_OFFLOAD_MULTI_SEGS，也就是多段发送能力。 因此不能把前面的“无 offload 简单路径”说成项目在真实 ixgbe 上必然选择的路径；路径选择必须以实际能力、配置和驱动回调为准。

只看这几行，解释为什么需要单独保存 lengths 
/* 按 flush_egress 的实际逻辑摘录，省略入口门禁 */
uint16_t sent = rte_eth_tx_burst(egress->port_id, worker->queue_id, packets, count);
output->tx_packets += sent;
for (uint16_t i = 0; i < sent; ++i)
    output->tx_bytes += lengths[i];
if (sent < count) {
    output->tx_drops += count - sent;
    output->tx_queue_drops += count - sent;
    free_packets(packets + sent, (uint16_t)(count - sent));

lengths 保存的是交接前的普通数字，访问它不需要访问已提交的包。 如果改成发送后读取 packets[i]->pkt_len，就把统计逻辑放到了不再拥有该对象的时段。 这类错误在慢设备上可能长期不明显，在快速完成或软件 PMD 上更容易暴露。

还要注意数组的身份：packets 是当前出口实际待发数组。 有些 RX 包已经因解析、规则或路由失败被丢弃，其他包可能走了另一个出口。 sent = 3 指这个出口数组的前三项，不是原始 RX burst 的前三项。

本项目这条发送路径没有调用 rte_eth_tx_prepare()，也没有通过 rte_eth_tx_done_cleanup() 定期催收。 这些 API 在本章用于理解机制和可选能力，不能据此声称项目已经实现相关功能。 现有路径中的报文改写自行维护所需校验和；要新增硬件卸载，应另行核对配置与元数据，而非只插入一个函数调用。

同一个 TX API，net_ring 为什么完全不同

项目软件集成测试用 rte_eth_from_rings() 建立端口。 net_ring 的 TX 把 mbuf 指针放入软件 ring，成功入队的对象由测试消费方取走并释放；没有物理 DMA、TX 描述符门铃和网卡 DD。 成功提交以后 worker 不再释放前缀的约定仍然成立，但后面的执行者变成软件消费者。

所以“由发送路径回收”是一条责任链，不保证一定由最初调用的 PMD 函数亲自完成每次 free。 查看 net_ring 的收发实现， 再与物理 PMD 比较，可以避免把 API 名称误认成硬件机制。

停机时为什么不能先把池销毁

退出时必须先阻止新的使用，并等使用资源的线程和设备按各自协议停止，再销毁底层内存。 如果 NIC 或 worker 仍可能访问数据，释放整个池会让尚未结束的访问落到已经失效的内存上。 这比漏掉几个空闲对象严重得多；设备 close 失败时也不能假定已经失去访问能力。

项目的 设备清理路径 依次尝试 stop 和 close，任何端口没有成功关闭都会保留共享池；关闭完成后再报告池占用并释放池。 多个端口可能共用同一个池，所以不能只看某一个出口已停止就释放整池。 这里保证的是资源退出顺序，不承诺停机前每个已接受包都送达了对端。

遇到发送问题，按证据把原因拆开

若 TX 经常返回不足，先看同一时间窗里的提交数量、接受数量、设备状态与队列可用资源； 若接受数量正常而池余量持续减少，再查 TX 在途、业务排队、完成报告与软件回收。 若本地接受与设备统计都增长而对端看不到，则继续核对线上报文、链路、对端过滤和上层接收条件。 这三种现象对应不同边界，不能都归为“发送失败”。

08 用变化条件检验自己的模型

先独立解释，再展开答案。浏览与展开不会记录为“已经掌握”。

1. TX 返回 3，能立即释放数组中的前 3 个 mbuf 吗？

不能。返回值划定的是已交接前缀，这些引用不再由应用处理。 网卡可能仍要 DMA 读取它们，或者软件 PMD 已交给另一个消费者。应用释放后对象可能被重新分配并写入新数据，从而破坏尚未结束的使用。

2. 提交 5 个包只接受 3 个，重试时从哪个位置开始？

只有后两个仍属于应用。 若策略允许重试，应从 packets + 3 开始处理剩余 2 个，并保留终止与释放条件。 重新提交全部 5 个会重复处理已移交对象。本项目选择直接释放未接受尾部。

3. 一个包由三段组成，TX 返回 1，表示只发送了第一段吗？

返回值以包为单位，表示这一个包已被接受。 在支持相应多段配置的路径中，驱动需要管理这条链对应的多个段；应用不能再把后两段当成未发送尾部自行释放。 描述符个数、mbuf 个数和包数并不总相等。

4. 网卡已经完成，为什么池可用量仍没有恢复？

完成依据成立与 CPU 执行回收是不同事件。 回收可能等待后续调用或批量条件；释放一个引用后也可能还有其他合法引用。 应追踪实际持有者并在正确的清理边界核对基线，不能只用瞬间池余量判断泄漏。 内置 lcore 缓存已包含在 rte_mempool_avail_count 的计数里，不能用它解释该总量减少。

5. tx_prepare 返回全部包数，能证明它们已发送或一定合法吗？

不能。prepare 不是提交，返回的是准备完成的前缀。 驱动未实现时还可能不检查而原样返回；真正发送仍需 TX burst，并处理它的实际接受数量。 prepare 可能修改校验和等字节，调用之前也要保证数据安全可写。

6. 把发送队列扩大一倍，能消除持续出口过载吗？

不能保证。 队列可以吸收更长的短时突发，但长期输入超过输出时，积压仍增长，并可能提高排队时延和 mbuf 占用。 需要增加实际服务能力、控制输入，或采用有界排队与明确丢弃策略。

7. 调用 tx_done_cleanup 返回 0，是否证明驱动泄漏了内存？

不能。 当前可能没有满足回收条件的对象，具体路径也可能按完整报告组回收。 先确认接口支持情况、设备完成进度、尾部是否可被观察，以及已有对象由谁持有，再判定是否异常。

8. 软件 ring 测试通过，证明了哪一段发送责任链？

证明范围由实际断言决定，例如 worker 正确交出成功前缀、释放失败尾部，以及消费者排空后资源恢复。 它没有物理 TX 描述符、DMA 读或网卡完成报告，因此不能证明这些硬件环节正确，也不能据此报告物理线速。

把 RX 与 TX 放在一起理解

RX 让设备获得可写空间，完成后把装有数据的对象交给应用； TX 让设备获得可读数据，满足完成与回收条件后结束发送路径持有的引用。 CPU 不必等待每个设备动作，但每个对象必须始终有明确的持有者、交接点和最终退出路径。
