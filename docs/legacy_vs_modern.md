# DPDK 17 旧模式 vs 当前现代模式

## 1. 文档目的

本文档用于说明：

- 过去在 DPDK 17 时代采用的 `igb_uio + KNI + 配套 ko + 用户态媒体面` 模式是什么
- 当前 `dpdk-dataplane-platform` 为什么不沿用那条运行时路径
- 两种模式的差异、适用场景和迁移思路是什么

## 2. 对比结论

### 旧模式

- 偏业务驱动
- 典型于运营商网元、虚拟化媒体面托管
- 目标是让用户态接管部分协议，其他协议回内核
- 依赖 `igb_uio/uio`、`rte_kni.ko` 等配套模块

### 当前现代模式

- 偏平台化、工程化、可演进
- 目标是构建现代 DPDK 用户态数据面平台
- 主线围绕：
  - ARP / IPv4 / UDP
  - 多核 / RSS
  - ACL / NAT
  - `rte_flow`
  - representor
  - transfer
  - SmartNIC / DPU

## 3. 总体对比表

| 维度 | DPDK 17 旧模式 | 当前现代模式 |
|------|----------------|--------------|
| 项目目标 | 媒体面托管 + 内核协同 | 现代用户态数据面平台 |
| 驱动绑定 | `igb_uio/uio` 常见 | 现代方式，面向当前平台化环境 |
| 内核协同 | 通过 KNI 回交内核 | 主线不依赖 KNI |
| 协议处理范围 | 常只托管关键协议（如 UDP） | 先软件路径，再演进到 offload / representor |
| 运行时复杂度 | 较高，依赖配套模块 | 更利于统一构建、统一测试 |
| 向 SmartNIC / DPU 演进 | 跳跃较大 | 路径更自然 |
| 面试表达 | 强调真实历史项目经验 | 强调现代数据面平台与可扩展性 |

## 4. 为什么当前项目不继续按旧模式实现

主要原因有四个。

### 4.1 当前主目标已经变化

当前项目不是为了复刻旧系统，而是为了：

- 系统化学习现代 DPDK 数据面平台设计
- 为更匹配当前岗位需求的方向做准备
- 能持续扩展到 `rte_flow` / representor / transfer / SmartNIC / DPU

如果主线仍然停留在 `igb_uio + KNI + 配套 ko`，项目重点会偏离现代能力栈。

### 4.2 旧模式会增加环境复杂度

如果保留旧模式运行时支持，需要额外处理：

- 历史版本 DPDK 构建
- 老式模块适配
- KNI 配置
- 不同内核版本间的兼容问题

这些问题会明显分散当前项目的主线精力。

### 4.3 当前项目更强调抽象与可演进性

当前项目关注的是：

- 软件数据路径抽象
- 多核并行模型
- ACL / NAT / 流表
- `rte_flow` pattern / action 建模
- representor / transfer 预留

这些内容与现代平台方向更一致。

### 4.4 旧经验可以通过文档保留，不必进入主线代码

你的旧经验并不会丢：

- 可以通过 `legacy_dpdk17_mode.md` 完整保留
- 可以在面试中作为真实业务经验讲述
- 可以映射到当前 Phase 1 和 Phase 4 的设计理解中

## 5. 旧经验如何迁移到当前现代项目

### 5.1 从“只托管 UDP”迁移为“聚焦关键流量的 pipeline”

旧项目里只托管 UDP，本质是聚焦关键流量。

在当前项目中，这可以演变为：

- pipeline 只优先处理关键业务流
- 其他流量按策略决定是否继续处理、丢弃或导出
- 后续可再对接 `rte_flow` / transfer 做更强的路径选择

### 5.2 从“回交内核”迁移为“更清晰的路径抽象”

旧项目通过 KNI 回交内核，本质上是在区分：

- 用户态托管路径
- 非托管路径

当前项目中，这种思想可以演变为：

- software path
- offload path
- transfer path
- 未来必要时再扩展其他路径

### 5.3 从“业务项目经验”迁移为“平台化表达”

旧项目更偏业务交付，当前项目更偏平台化设计。

这意味着你后续在面试中可以这样表达：

- 我做过 DPDK 17 时代的运营商网元媒体面托管架构
- 我知道用户态 fast path 与内核网络栈如何协同
- 我现在把那段经验抽象成一个现代用户态数据面平台项目，继续向 `rte_flow`、representor 和 SmartNIC / DPU 方向演进

## 6. 对当前项目的最终结论

当前 `dpdk-dataplane-platform` 的决策是：

- **代码主线只保留现代方式**
- **不支持 DPDK 17 旧模式的运行时实现**
- **用专门文档保留 DPDK 17 历史经验与架构说明**

这是一个刻意的工程取舍。

它的目的不是否定旧经验，而是：

- 让当前项目保持现代化、工程化和可扩展性
- 让学习路径与当前市场岗位需求更一致
- 让历史经验成为加分项，而不是当前主线的包袱
