# M5 首项：M4 配置持久化与进程重启恢复

本项为 M4 独立 C API 增加持久配置和受管理的运行实例，不把它登记为完整 M5 生产化完成。
核心入口是 [flow_state.h](../include/dppd/flow_state.h)，实现分别为
[配置编码与文件写入](../lib/control/flow_state.c) 和 [运行实例与恢复](../lib/control/flow_store.c)。

## 保存什么

一份 `DPPM4CFG` revision 1 文件保存同一服务的完整期望状态：

| 内容 | 持久字段 |
| --- | --- |
| 服务 | 软件/原生模式、安装端口、逻辑容量、超时 |
| 队列 | 队列数量、深度、每队列实际流容量、规则所属队列 |
| 配额 | 全局及每端口九类资源额度、ticket 容量 |
| 模板 | 稳定模板键、示例 IR、掩码、动态动作位、实际容量及借用池容量 |
| 共享 COUNT | 完整 ID、generation、端口和域、下一次可用 generation |
| 规则 | 完整 IR、精确 generation、所属模板键、全局规则修订号 |

文件不保存驱动指针、flow 句柄、lease/ticket、未完成请求、完成回执、COUNT 数值或已经过去的 AGE 时间。
规则复用既有 v5 的规范编码，IPv6、动作参数和 64 位共享身份保持完整。
外层文件使用独立 magic/version，不改变旧 v2–v5 快照，也不会猜测旧快照缺少的模板及队列配置。

配置在一个实例运行期间保持不变；创建、更新、精确删除和自动 AGE 导致的规则变化自动保存。
修改模板、共享对象定义或额度须先停用并关闭实例，再通过纯配置 API 保存并重新打开。

## 保存与回执

`dppd_flow_state_initialize` 在写锁内检查文件不存在，拒绝覆盖已有策略。
`dppd_flow_state_save` 用于离线保存完整配置；已有在线实例持有同一锁时返回 `EBUSY`。
保存过程为同目录 0600 临时文件、完整写入、文件 fsync、rename、目录 fsync。
短写和 EINTR 会继续写，零长度写和 I/O 失败不能得到成功结果。

`dppd_flow_store` 独占所创建的模板、共享对象、队列、规则服务及软件 classifier 写入。
普通异步提交只表示受理。实际整批发布后，`process` 先保存完整配置，成功后才允许 `collect`
返回成功回执。并发消费者也受同一实例锁约束，不能在写盘完成前抢先领取结果。

写盘失败置 `dirty`，封闭新写入、继续推进和结果领取，保留实例及已发布状态。
`flush` 重试成功才更新 `durable_revision` 并解除 dirty；关闭不会静默丢弃未持久化状态。
rename 以前失败保留旧快照；目录同步失败时新文件可能已可见，仍返回失败并保持 dirty。
若下层修订号已经变化但仍报告发布不确定，保留最后可靠快照，不允许普通 flush 冒充已一致。

进程若在实际发布和持久化完成之间退出，未确认的请求可能丢失；重启使用最后一份完整可读的配置。
已经持久化但尚未送达调用方的回执也可能丢失，未来北向服务仍需自己的请求幂等和会话协议。
本项不承诺文件替换与硬件报文切换之间存在跨系统原子事务。

## 恢复顺序与就绪

打开配置先取得进程间独占写锁，再检查长度、CRC32、版本、规范编码、引用关系和资源容量。
损坏、截断及不规范编码返回 `EBADMSG`，未知格式版本返回 `EPROTONOSUPPORT`，不会调用驱动。
相对路径固定到父目录绝对路径，后续切换工作目录不会改变保存位置。

恢复按以下顺序执行：

1. 原生模式由调用方独立核对目标端点并证明没有旧对象，再配置真实流队列和对象池
2. 创建配额对象，按旧 generation 升序重建共享 COUNT，恢复下一次可用代次
3. 重建模板，将文件内稳定键解析为本进程的新凭据
4. 按保存的队列及精确旧版本，分批准备全部实际 flow 和期望账本
5. 全部成功后一次编译并发布完整软件 classifier，再开放 ready 和 worker 访问

恢复不会按条数重新编号，全局修订号和删除产生的版本空洞保留。
共享对象也不会因重启复用已经删除的旧代次；未使用过的共享定义仍会恢复。
COUNT 从零开始，AGE 使用新 context 并重新开始闲置计时，旧通知和句柄不从磁盘复活。

恢复失败先逆序清理已创建对象，普通失败清理完成后返回原错误及空实例。
若创建仍未完成、结果未知或清理失败，返回 `EUCLEAN` 及保留实际凭据的非就绪实例。
调用者必须保留它，查询状态并重试 `close`；写锁、配额和依赖引用在此期间继续保留。
不能丢弃实例后再次盲目安装，也不能以超时为理由释放正在创建的对象。

## 正常停机

集成方先停止并注销所有 worker，领取全部用户任务结果，再关闭实例。
关闭先一次发布空 classifier，然后精确回收流、队列、模板及共享对象，不把停机删除写成策略删除。
文件中的期望状态保持，下一次打开仍能恢复；规则版本耗尽也可以正常回收实际对象。
关闭等待有界，驱动仍有完成或暂态清理失败时可能需要再次调用，不能提前释放写锁。

`ready=false` 或 dirty/隔离时，集成方应停止继续接入业务。
组件不会自动停止借用 classifier 的外部 worker，也不接管外部 ethdev、路由或管理网卡生命周期。

## 工具与使用

```sh
# 初始化一份软件配置：端口 7，逻辑容量 64，两个队列，深度 64
build-perf/dppd-flow-state init-software /absolute/path/m4.state 7 64 2 64

# 只校验文件并输出摘要
build-perf/dppd-flow-state check /absolute/path/m4.state

# 真实重建及回收软件对象，不启动转发 worker，也不改写期望配置
build-perf/dppd-flow-state restore-check /absolute/path/m4.state
```

初始化工具提供稳定键为 1 的 Ethernet DROP 模板；更完整的模板、共享对象和初始规则
通过 `dppd_flow_state` 纯数据结构构造并保存。运行时使用 `flow_store_submit/update/remove`
操作规则，持续调用 `process`，通过 `collect` 取得已经持久化的最终结果。

原生恢复必须提供 `verify_empty` 回调，并由集成方准备 ethdev、稳定端点绑定和真实清空证据。
不提供回调明确返回 `ENOTSUP`，检查不通过不调用创建；数值 port_id 本身不是设备身份凭证。
工具没有独立硬件清空证明，因此 `restore-check` 明确拒绝原生配置。

## 验收与限制

统一入口为：

```sh
python3 scripts/verify_m5.py --build-dir build-perf
```

它重新运行全部单测、核心/M3/M4 回归，再启动两个全新 EAL 进程，在真实 net_ring、mbuf
和正式 worker 上验证持久化更新、突然退出、精确版本恢复、COUNT 归零、完整报文字节和缓冲回收。
前后两个进程合计 96 包，退出清理不能改写保存的期望配置。

单测另外覆盖真实 SIGKILL 与 exec、跨进程写锁、所有恢复 calloc 位置分别失败、
写盘各阶段故障、未完成创建、失败补偿、共享版本空洞、AGE 删除落盘、相对路径及未知发布封闭。
16384 条测试完整重放并逐条查询精确版本，再回收实际对象并复查期望文件保持不变。
先前按小批反复编译的软件路径在 sanitizer 大规模测试触发 120 秒超时，原始失败证据已保留；
修复改为恢复完成时一次发布、退出时一次清空，未延长测试超时或降低既有性能门槛。
