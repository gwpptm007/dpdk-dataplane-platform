# 规则增删改：技术原理、方案选择与实现

这套代码解决的核心问题是：**配置在变化，报文处理仍要继续；变更成功后各处状态要一致，失败后要知道哪些动作已经发生**。

截至 2026-11-03，已结合源码走读同步规则管理主线。本篇把其中可复用的技术整理为参考，不再按函数逐行讲解。以后遇到批量、异步或硬件接口，先核对它的提交边界，再复用这里的原理。

通用原理可以复用，但具体选型并非唯一：本项目选择了单管理写线程、内存规则记录、软件快照发布、QSBR 延迟回收和完整文件保存。这些选择适合什么、付出什么代价，见下文。

复习主线先看第 1、2、10 节；忘记具体原理时查第 3～9 节；迁移到其他项目时查第 11 节的选型比较。

## 1. 先看整体：一次变更影响三处状态

```text
用户命令 → 管理请求 → 控制层：检查、规划、协调安装
                         │
                         ├─ 实际规则状态（软件表／网卡）
                         │    软件：active 指向的规则快照和 exact/ACL
                         │    硬件：网卡规则安装记录及驱动创建的 flow 对象
                         │
                         ├─ 控制面记录：service->rules
                         │    保存每条规则的配置、版本和查找索引
                         │
                         └─ 配置文件
                              保存重启后重新创建规则所需的数据
```

这三处职责不同，也不是同时更新：

| 状态 | 用于什么 | 不包含什么 |
| --- | --- | --- |
| 实际规则状态（软件表／网卡） | 让软件或硬件实际处理报文 | 不等同于磁盘上的恢复配置 |
| `service->rules` | 按 ID 查询、检查版本、列举配置 | 不直接替代 worker 使用的匹配表 |
| 配置文件 | 重启后读取并重新安装 | 不保存可跨进程使用的驱动指针，也不保存累计 COUNT |

因此，必须分别判断“实际规则已生效”“控制面记录已更新”“配置已保存”。一个错误返回值不能说明前面的操作都没发生。

源码入口：[CLI 参数解析](../../app/dppctl/main.c)、[管理请求分发](../../lib/management/server.c)、[控制层](../../lib/control/control.c)。

## 2. 新建、修改、删除共用的流程

```text
新建：检查请求 → 选择规则执行位置 → 安装新规则 → 写入控制面记录 → 收尾 → 保存配置

修改：检查旧版本 → 选择规则执行位置 → 安装新版本 → 删除旧版本
                                        → 更新控制面记录 → 收尾 → 保存配置

删除：检查旧版本 → 删除软件表或网卡中的规则 → 移除控制面记录和索引 → 保存配置
```

这里的修改流程指 `control_apply_impl()` 的单条同步路径。软件整批更新另有一次发布的实现，不能把单条路径的中间状态套到所有接口上。

### 用同一个例子串起来

假设规则集合整体版本为 12，规则 ID 20 的当前版本为 7。本次修改目的端口匹配条件，调用方携带 `expected_generation = 7`。

```text
检查：当前规则版本确实为 7
候选：ID 20，新内容，新版本 13（整体版本 12 + 1）

实际安装版本：[20/7] → [20/7, 20/13] → [20/13]
记录：一直保留 20/7 ─────────→ 更新为 20/13
文件：最后保存更新后的完整配置
```

新版本安装失败，就清理本次资源；旧版本删除失败，就尝试撤销新版本；清理也失败则进入恢复隔离，阻止继续普通修改。

这种先装后删避免了“旧版本先删掉，新版本却装不上”的窗口，但有新旧并存阶段，还需要额外容量。它不承诺整个替换过程对报文原子可见。

## 3. 统一规则描述与执行规划

`struct dppd_rule` 是独立于 CPU 查表和网卡执行方式的统一规则描述，包括身份、版本、安装位置、匹配条件和动作。它描述“想做什么”，具体软件表和硬件对象描述“怎样执行”。

```text
统一规则 dppd_rule
      → planner 检查拓扑、模式和能力
      → execution_plan 选择 SOFTWARE 或 RTE_FLOW
      → 所选规则安装接口的 validate / prepare / commit
```

| 技术选择 | 作用 | 代价和边界 |
| --- | --- | --- |
| 统一规则描述，分别转换为软件表条目或网卡规则 | CLI、查询和保存共用一种配置表达 | 统一表达不保证 CPU 和网卡都支持每种规则语义 |
| 规划与安装分开 | 安装前就能说明选择的软件/硬件及原因 | 选中硬件后仍要做驱动校验，校验成功也不保证创建不会失败 |
| 硬件优先时有条件回退 | 支持时卸载，不支持时可考虑软件 | 必须语义等价且满足失败阶段条件，不能把部分创建错误当作安全回退 |

当前 planner 对连接跟踪、ND、IPv6、AGE、共享计数等还有限制；“硬件不可用就随便走软件”不是本项目的规则。具体条件以 `dppd_plan_rule()` 和软件规则校验与驱动校验为准。

源码：[rule.h](../../include/dppd/rule.h)、[planner.c](../../lib/control/planner.c)。

## 4. 版本检查：防止旧请求覆盖新配置

三种数值应分清：

| 名称 | 含义 | 例子 |
| --- | --- | --- |
| 规则 ID | 哪条规则 | 20 |
| 规则 `generation` | 这条规则当前是哪一版 | 7 |
| 规则集合整体版本 | 整个配置集合最近一次变更的修订号 | 12 |

`expected_generation` 是调用方对旧状态的要求，不是要求写入的新版本。

```text
调用方读到规则 20 的版本 7
其他请求已将其更新为版本 9
调用方仍携带 expected = 7 来修改或删除
  → -ESTALE，拒绝操作
```

这是乐观版本检查：操作前比较版本，阻止基于旧状态的修改。它不是锁，也不提供多写线程下自动原子提交；当前管理主线程串行执行配置请求，是控制面版本分配的前提之一。

单条接口的特殊情况：

- 规则不存在时，新建接受预期版本 `0` 或 `ANY`；`ANY` 是跳过预期版本限制的保留值
- 单条 apply 发现已有规则内容完全相同，会先返回 `UNCHANGED`，不再检查旧版本，也不增加版本
- 单条删除发现规则不存在，预期为 `0` 或 `ANY` 时可成功返回 `removed = false`；指定精确旧版本则返回 `-ESTALE`
- 批量接口的预期版本要求更严格，不能直接照搬单条接口的 `ANY` 和重复请求语义

变更成功时推进整体版本，修改后的规则取得该新版本；删除也推进整体版本，重新创建相同 ID 时不会沿用已删版本。其他未修改规则保留自己的版本。

同内容 apply 的幂等性仅表示重复提交不会重复安装；它不等同于持久请求 ID、响应丢失恢复或跨重启的完整幂等协议。

源码：[rule_repository.c](../../lib/control/rule_repository.c)，函数 `dppd_rule_repository_apply()`、`dppd_rule_repository_remove()`。较新的持久请求能力另见 [M5 持久请求](../m5_durable_requests.md)。

## 5. 回调接口：让软件和硬件共用事务流程

`dppd_transaction_backend` 保存对象地址和函数指针，用 C 的函数指针将不同的规则安装函数组织成统一接口。

```c
.context = backend,
.prepare = transaction_prepare,
.rollback = transaction_rollback,
```

初始化保存函数地址，调用时才执行函数：

```text
backend->prepare(backend->context, item, &item->backend_token)
          │
          └─ 根据初始化时绑定的函数地址进入对应软件或硬件实现
```

`context` 将软件规则或网卡规则的管理信息传回回调；`token` 是事务保存并原样转交的资源凭据。软件规则安装函数把 `pending` 地址存入 token，网卡规则安装函数可以使用自己的表示，事务不解释其内容。

选择函数指针接口，可以复用阶段调度和故障处理；代价是阅读时要追踪“接口在哪里赋值”，并遵守资源所有权约定。它不是按成员名自动查找实现，也不意味着异步执行。

源码：[transaction.h](../../include/dppd/transaction.h)、[软件接口绑定](../../lib/dataplane/software_backend.c)、[硬件接口绑定](../../lib/offload/rte_flow_backend.c)。

## 6. 分阶段事务：安装与补偿

| 阶段 | 职责 | 失败时怎样处理 |
| --- | --- | --- |
| validate | 检查软件表或网卡是否支持该规则，不占安装资源 | 直接返回错误 |
| prepare | 准备可撤销资源，交回 token | 清理已准备资源，失败条目留下的资源也要清理 |
| commit | 使用准备资源安装或发布规则 | 尝试撤销已提交效果及其他准备资源 |
| rollback | 释放准备资源或删除本次安装的版本 | 记录清理错误，继续尝试其他条目 |
| finalize | 放弃事务回滚，释放临时资源 | 保留已安装规则，不等同于保存配置成功 |

通用事务执行顺序是“全部 validate → 全部 prepare → 逐条 commit”；失败按逆序回滚。它是应用内的分阶段安装和补偿机制，不提供数据库事务那样的完整原子隔离，也不是跨进程分布式两阶段提交。

```text
软件 prepare：分配 pending，保存待安装规则
软件 commit ：将规则复制进新快照，发布后设置 pending->published
软件 rollback：未发布 → 释放 pending
                已发布 → 删除本次 ID + generation，再释放 pending
软件 finalize：只释放 pending，已发布规则继续存在
```

关键区分：`failure_code` 记录原操作错误；`rollback_code` 记录清理错误。返回安装错误时，可能已经完成清理，也可能还有残留，必须同时检查清理结果。

清理失败进入恢复隔离，阻止普通修改，交给恢复流程处理；设置隔离状态本身不会自动清除残留规则。

源码：[transaction.c](../../lib/control/transaction.c) 的 `dppd_transaction_run()`、`rollback_items()`；[software_backend.c](../../lib/dataplane/software_backend.c) 的 `transaction_rollback()`。

## 7. 软件更新：复制、发布、延迟回收

### 为什么使用快照

报文读取远多于配置修改。若在 worker 正在使用的表里原地改条件、动作和索引，读者可能读到只更新了一半的状态。

本项目将修改成本放到控制面：

```text
active → A，worker 已取得 A
           │ 复制规则内容，共享已有计数器
           ▼
           B → 修改规则 → 重建 exact/ACL → 原子切换 active → B

已有读者继续用 A；后续读者取得 B；A 暂时放入 retired 链表
```

发布后不再原地修改规则内容和匹配索引，计数器仍允许原子更新。release/acquire 配合使取得新快照的读者看到已完成的初始化；原子指针切换本身不负责旧内存的存活时间。

### 为什么还要 QSBR

把 `active` 从 A 换成 B，不会改变 worker 手里的局部 A 指针。立即释放 A 就会造成释放后访问。

QSBR 利用读者主动报告安全点：读者确认不再持有前一阶段的快照引用，控制面据此判断旧快照何时可回收。

```text
发布 B → 为旧 A 记录回收进度 token
       → 相关在线读者通过安全点
       → 检查通过 → 销毁 A
```

这不是固定延时、扫描全部指针或按报文计引用。读者若长期不报告安全点，旧快照就可能长期占用内存。离线、注册和注销也必须符合 QSBR 的使用约定。

### 计数器引用为什么单独管理

快照 A、B 中同一未修改规则版本可以共用计数器 M。复制快照增加 M 的引用，销毁快照归还引用，最后一个引用释放时才销毁 M。

```text
A → M ← B       references = 2
销毁 A          references = 1，M 仍可使用
销毁 B          references = 0，释放 M
```

这里引用数统计持有它的快照，不是 worker 数量或命中包数。未修改版本的 COUNT 连续，新规则版本重新创建计数器；累计值也不随文件恢复。

源码：[software_backend.c](../../lib/dataplane/software_backend.c) 的 `snapshot_clone()`、`publish_locked()`、`reclaim_locked()`、`metrics_put()`；[worker.c](../../lib/dataplane/worker.c) 中的安全点上报。

## 8. 索引与匹配表：不同查询使用不同结构

| 结构 | 当前实现和用途 | 取舍 |
| --- | --- | --- |
| 控制面的 `records[]` | 稳定槽位保存完整规则 | 删除后可复用槽位，不搬动全部规则对象 |
| `slot_index` | 有序槽位编号数组，二分定位 ID，空闲槽链复用 | 查找 O(log N)，插入/删除有序编号可能 O(N)；未采用哈希表 |
| 软件 exact 表 | 哈希定位完整键，再比较完整内容 | 完整地址和端口适用，哈希冲突仍需比较，不能替代范围规则 |
| 软件 ACL 表 | 按入口及规则顺序组织，二分定位入口范围，再检查条件 | 支持掩码和范围；入口内仍需扫描，不是整次分类都 O(log N) |

控制面索引使用 `(rule_id, 0)` 定位记录，记录内部另有真实 generation；索引键中的零不是规则版本。查询软件规则的具体安装版本时则同时比较 ID 和 generation。

exact/ACL 返回的 tag 用于定位快照内规则槽位，通常为 `slot + 1`，零表示未命中；tag、规则 ID、规则版本是不同概念。两张表查找候选，软件规则匹配函数再按规则顺序选定动作，不能简单认为 exact 命中就无条件压过 ACL。

这里的 ACL 是项目自己的软件实现，不应仅凭名称当作 DPDK `rte_acl` 算法。硬件 `rte_flow` 是否支持相同规则还需另行验证。

源码：[slot_index.c](../../lib/control/slot_index.c)、[exact.c](../../lib/dataplane/exact.c)、[acl.c](../../lib/dataplane/acl.c)。

## 9. 文件保存：完整快照与原子替换

`dppd_persistence_save_with_shared()` 把全部规则和共享计数器创建配置写入文件，供重启时重新创建规则。它不负责把当前规则写入软件表或下发到网卡。

```text
复制、检查配置 → 选择文件格式 → 显式编码、计算 CRC
  → 写同目录临时文件 → fsync 文件 → rename 替换 → fsync 父目录
```

| 技术 | 为什么使用 | 边界 |
| --- | --- | --- |
| 按字段显式编码 | 不依赖 C 结构体填充和主机内存布局 | 需要维护格式版本及兼容读取 |
| CRC | 读取时检测内容损坏 | 不是防篡改签名 |
| 同目录临时文件与 rename | 完整写好后再原子替换目标文件 | 替换与断电持久性是不同问题 |
| 文件 fsync、父目录 fsync | 分别同步文件内容及文件名变更 | rename 后目录同步失败，新文件已可见，仍返回错误 |
| 保存完整配置 | 文件包含一份完整恢复数据，规则与共享定义一起检查 | 每次需重新编码和写入全部配置；不是增量日志 |

普通整数元数据按小端编码，规则中已经按网络字节序保存的 IP/端口直接复制。v2/v3/v4/v5 是文件格式版本，和规则 generation 无关，分别按 IPv6、AGE 和共享配置的需要升级。

当前顺序是先生效、后保存。保存失败设置 `persistence_dirty` 并返回 `-EUCLEAN`，不撤销已生效规则；下一次普通修改前先补写当前配置，仍失败则拒绝继续修改。未配置保存路径时跳过文件保存。

这不是先写日志再提交的 WAL，也不是实际规则、内存记录和磁盘之间的跨介质原子事务。旧规则文件存在，不代表里面一定有最近已生效的变更。

源码：[persistence.c](../../lib/control/persistence.c)、[control.c](../../lib/control/control.c) 的 `persist_current_repository()`、`persistence_write_preflight()`。文件基础格式另见 [持久化格式 v2](../persistence_snapshot_v2.md)，其 v2 布局不代表当前所有文件都固定写 v2。

## 10. 一致性边界与批量接口

| 问题 | 当前同步路径的回答 |
| --- | --- |
| 管理配置由谁写？ | 普通管理循环在主线程串行处理；软件规则的修改和回收另由 writer_lock 保护 |
| worker 会看到半张匹配表吗？ | 单次快照发布前已构建完整匹配表；已有读者仍可用旧表 |
| 单条修改的新旧版本会并存吗？ | 会，先安装新版本再删除旧版本 |
| 通用事务提交多条时，会看到部分成功吗？ | 可能，逐条 commit 可多次发布，回滚不消除已经被读者观察过的效果 |
| 纯软件整批替换是否也逐条发布？ | 特定软件批量接口在副本完成整批修改后一次发布，接口条件须单独核对 |
| 安装成功是否等于文件保存成功？ | 否，规则安装提交、控制面记录更新和保存分别完成 |
| `-EUCLEAN` 是否总表示实际规则残留？ | 否，也可能表示已生效但保存失败，应结合阶段、dirty 和恢复状态判断 |

区分两种原子性：**一次 active 指针切换的可见性**，与**一个管理请求涉及的全部步骤能否一起成功**。本项目不能仅凭前者就宣称后者也成立。

批量与后续能力参考：[软件整批发布](../m4_software_publication.md)、[批量更新验证记录](../validation_batch_update.md)、[持久请求](../m5_durable_requests.md)。这些文档记录各自范围，不代表本次已经逐段学习过所有实现。

## 11. 换个项目时怎样判断选型

先提出约束，再选机制，不必机械照搬整套实现：

| 约束 | 本项目的选择 | 其他可能选择及主要代价 |
| --- | --- | --- |
| 读报文频繁、改配置较少 | 写时复制与完整匹配表重建 | 原地修改加锁更直观，但读写会互相等待 |
| 读者能明确报告安全点 | QSBR 延迟回收 | 每个读者持引用也能管理生命周期，但要处理逐次获取/归还及竞争 |
| 需要支持 CPU 查表和网卡执行两种方式 | 统一规则 + planner + 回调表 | 分别实现全流程可以少一层抽象，但校验、版本和失败处理容易重复 |
| 规则有界，要求稳定槽位和有序列举 | 预分配槽位 + 有序索引 | 哈希索引通常利于精确查找，但有序列举和容量管理需另做设计 |
| 实际规则安装难以整体撤销 | 分阶段安装、逆序补偿、失败隔离 | 完整事务依赖软件表或网卡额外提供的能力，不能仅改接口名称就获得 |
| 配置规模允许每次完整保存 | 文件快照 + 原子替换 | 日志或数据库可承担不同持久化需求，但需设计重放、事务和恢复规则 |
