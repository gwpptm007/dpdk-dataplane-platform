dppd 从准备到收包，再到退出

用网口 0 ↔ 网口 1 转发的例子，先看四段全景和两类分工，再对照源码。主线全部显示，源码可以按需展开。

当前先重新梳理整体关系，连接跟踪与 NAT 暂缓。

下面按阶段 0～5 看“谁来做、准备什么、做完多了什么”。代码讲过和页面打开过，都不作为已经掌握的依据。

全景只分四段：准备机器 → 准备程序 → 持续运行 → 安全退出

① 程序外准备机器

按运行模式准备大页、权限和网卡驱动，再执行 dppd

② 主线程准备准备程序

EAL 与参数 → 内存池和队列 → 控制服务与管理入口

③ 多线程并行持续运行

主线程管理配置与设备；worker 一轮轮处理报文

④ 主线程收尾安全退出

关闭入口 → 通知并等待 worker → 释放规则和设备 → 清理 EAL

前一段是在为后一段创造条件。“网口启动了”“worker 开始收包了”“已经发出停止请求”“worker 已退出”是不同状态。

固定例子：两个网口、两个 worker

网口 0→程序处理报文→网口 1

我们要让进入网口 0 的包，经软件检查后从网口 1 发出，反向同理。先采用静态端口配对，不启用路由、连接跟踪、NAT 和 ND。

两个网口：0、1两个 worker每网口两个 RX/TX 队列每次收包上限：32

为解释方便，假设主 lcore 为 0、选出的 worker lcore 为 1 和 2，两个网口在同一个 NUMA 节点。编号与硬件路径均为示例，不代表当前电脑的运行状态。

运行时只有两类分工，先别把它们混在一起

主线程：准备、管理、收尾

  • 启动时创建运行资源、绑定对象
  • 运行时处理 dppctl 请求、检查设备和 worker、输出统计
  • 退出时发出停止请求，等待任务结束后再释放资源

主线程休眠 100 毫秒时，其他线程的 worker 继续运行

worker：按队列反复处理报文

  • worker 0：轮询两个网口各自的 RX 队列 0
  • worker 1：轮询两个网口各自的 RX 队列 1
  • 每轮执行 RX burst → process_batch → 转发或释放

两个网口、每网口两个队列，对应两个 worker，不是四个

示例分流关系（不是每包轮流分配）
RSS → 网口 0 的 RX 队列 0 → worker 0 → 示例 lcore 1
RSS → 网口 0 的 RX 队列 1 → worker 1 → 示例 lcore 2

RSS 选择 RX 队列；runtime 把 queue_id 与 lcore_id 放在 worker 配置中
启动时将这份配置传给工作函数，收包时按同一个 queue_id 读取

阶段 0

先准备机器，程序还没运行

调用 rte_eal_init 之前，大页和网卡由谁准备？

Linux 管理员或部署脚本先准备运行条件。采用大页和 VFIO 的物理网卡路径时，先预留大页、准备访问权限，再加载 VFIO 并绑定要使用的网卡。这里的操作在 dppd 进程之外。

Linux 主机
  ├─ 预留大页、按环境准备挂载和权限
  └─ 按 PMD 要求准备内核驱动与设备绑定
       ↓
  执行 dppd，进入 main
走到这里：机器具备运行条件，dppd 还没有创建自己的报文池或开始处理包
本项目没有自动预留大页的脚本；bind_nic.sh 只提供 VFIO 加载与绑定，run_platform.sh 只执行程序。mlx5 等驱动不照搬 VFIO 解绑步骤，--no-huge 和虚拟设备也有不同前提

scripts/bind_nic.sh · scripts/run_platform.sh

哪些参数交给 DPDK，哪些交给本项目？

阶段 2

把收包需要的人和工具准备好

网口、队列、mbuf 池和 worker 是怎样接起来的？

runtime_init 先给 worker 分配 lcore 和队列编号，再调用 devices_init 创建 mbuf 池、配置 RX/TX 队列并启动网口。此时准备的是工作配置和设备，业务循环还没有开始。

runtime_init
  ├─ worker 0：queue_id 0，示例选中 lcore 1
  ├─ worker 1：queue_id 1，示例选中 lcore 2
  └─ devices_init
       → 创建 mbuf 池
       → 每个网口建立 RX/TX 队列 0、1
       → RX 队列记录使用哪个池
       → 启动网口
走到这里：收发资源就位、网口已启动；worker 配置仍为 IDLE，尚未进入业务循环
nb_queues 是每网口的队列数，也决定 worker 数。描述符默认每队列请求 1024 个并由设备调整，burst 32 只是每次收包上限，不要求凑齐

阶段 3

准备配置管理，把对象连接起来

worker 从哪里取得规则？dppctl 怎样找到程序？

main 初始化 control，并把 control 持有的软件后端地址绑定到 runtime。随后按需恢复配置、创建管理 socket。worker 启动后通过 runtime 取得后端；dppctl 则通过 socket 发送管理请求。

control.software ──绑定地址──→ runtime.software_backend
                                      ↑
                                  worker 使用

dppctl ──Unix socket──→ management ──处理请求──→ control
走到这里：数据面可以找到规则后端，管理入口也已建立，后续主线程循环负责处理请求
此处只是准备和绑定对象；软件规则如何发布已经另有原理文档，不在这里重新展开

阶段 4

开始运行：主线程管理，worker 收包

调用 remote_launch 后，是谁在执行收包函数？

runtime_start 将工作函数和 worker 地址提交给选定 lcore。EAL 的工作线程执行 worker_main，完成规则读者注册后发布 RUNNING，再循环收包。主线程则继续执行管理循环，两边并行。

主线程：runtime_start → 提交 worker 任务 → 管理循环
                           │
                           ├─ lcore 1：worker 0，轮询各网口队列 0
                           └─ lcore 2：worker 1，轮询各网口队列 1

worker：RX burst → process_batch → 转发或释放 → 下一轮
主线程：检查设备/worker → 处理管理请求、维护统计 → 休眠后下一轮
走到这里：worker 正在处理包，主线程维持管理和监控；主线程休眠不会让 worker 一起休眠
remote_launch 提交成功与 worker 已完成准备是两件事。STARTING 表示启动中，worker 完成注册后才报告 RUNNING；RSS 选择队列，runtime 决定哪个 lcore 的 worker 轮询它

怎么接下一步：收到退出信号或发生无法继续的错误时，主线程进入停止流程

阶段 5

先等人停下来，再收走工具

为什么发出停止请求后，不能马上释放内存？

request_stop 只设置停止标记。worker 观察到后退出循环、注销规则读者并返回；主线程必须通过 wait 确认任务结束，才继续清理规则、设备和内存池。

关闭管理入口
  → request_stop：发出停止请求
  → worker：退出循环、注销读者、返回
  → wait：主线程确认任务已结束
  → 清理 control
  → 清理 runtime：关闭网口，再释放 mbuf 池
  → 清理 EAL，进程退出
走到这里：正常清理后，业务线程、规则对象、设备和池依次释放，最后结束 DPDK 环境
STOP 请求不等于任务已退出；网口关闭前驱动仍可能持有 mbuf，所以池必须后释放。cleanup_* 是标签，goto 跳过去以后继续向下执行

每走完一段，程序到底变成了什么状态？

走到哪里已经完成什么后面还要做什么
EAL 返回DPDK 基础环境和设备探测完成建立项目的池、队列和业务对象
runtime_init 返回worker 配置、池、队列就位，网口已启动准备控制关联，再提交 worker 任务
remote_launch 成功启动任务提交成功worker 完成读者注册并报告 RUNNING
worker 为 RUNNING工作函数已完成前置准备，进入业务循环持续收包，直至停止或门禁生效
request_stop 已调用停止标记已设置worker 退出循环，主线程等待返回
worker 全部返回不会再继续使用规则和设备清理后端、关闭设备、释放池，最后清理 EAL

看到术语时，先用这张表翻译

代码里的名字在这份例子里怎么理解
网口 / port程序收发报文的入口或出口，用 DPDK port ID 标识
RX / TX 队列RX 是接收通道，TX 是发送通道；不同网口的队列 0 是各自独立的队列
mbuf / poolmbuf 保存报文描述信息并关联数据缓冲；pool 把这些对象集中起来供反复取用和归还
worker / lcoreworker 是项目的一份工作配置及其收包任务；lcore 是 DPDK 安排任务执行的编号，二者与队列分别编号
EAL / PMDEAL 准备 DPDK 基础环境；PMD 是具体设备的用户态驱动实现，负责队列配置和收发操作
config / runtimeconfig 描述启动要求；runtime 保存按要求创建的设备、worker 及运行对象
control / managementcontrol 负责配置规则；management 通过 socket 接收请求并交给控制层
RSS / QSBRRSS 把报文分到 RX 队列；QSBR 帮助确认旧规则表何时不再被读者使用。二者解决不同问题
