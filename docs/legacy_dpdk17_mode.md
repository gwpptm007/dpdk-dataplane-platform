# DPDK 17 旧模式说明：运营商网元媒体面托管架构

## 1. 文档目的

本文档用于沉淀一类在 DPDK 17 时代常见、并且在运营商网元与虚拟化环境中实际使用过的集成模式：

- 用户态 DPDK 进程托管媒体面
- 控制面与媒体面分离
- 媒体面从网卡收包并解析业务流量
- 只保留特定协议（例如 UDP）在用户态数据面中处理
- 其他协议通过 KNI 回交内核协议栈
- 同时依赖 `igb_uio/uio`、`rte_kni.ko` 等配套模块

这份文档只是**历史经验说明**，不作为当前 `dpdk-dataplane-platform` 的运行时支持目标。

## 2. 典型应用背景

这种模式通常出现在：

- 运营商网元接入/转发场景
- 虚拟化平台中的媒体面托管模块
- 控制面与媒体面分离的网络功能模块
- 对特定协议进行高性能处理，同时保留部分流量走内核协议栈的混合数据路径场景

## 3. 典型架构

```text
物理网卡
  ↓
igb_uio / uio 绑定后的 DPDK PMD 收包
  ↓
用户态媒体面进程
  ├─ 解析 Ethernet / ARP / IPv4 / UDP
  ├─ 识别属于哪个网元 / 业务节点
  ├─ 重写 MAC / ARP / IP / UDP
  ├─ 转发到下一节点
  └─ 非 UDP 或未托管协议 → 通过 KNI 回交内核
```

## 4. 为什么当时这样设计

### 4.1 为什么媒体面使用 DPDK

因为媒体面需要：

- 高吞吐收包/发包
- 可控的用户态数据路径
- 只处理特定业务流量
- 对部分报文做快速解析、识别、改写和转发

在这种场景下，DPDK 负责托管媒体面是合理的。

### 4.2 为什么只保留 UDP

在很多运营商网元与媒体处理场景中，真正关注的是：

- UDP 承载的媒体流或业务消息
- 基于 UDP 的节点识别与后续转发

因此，DPDK 媒体面只保留 UDP 路径，可以减少用户态处理范围，把注意力集中到高价值流量上。

### 4.3 为什么其他协议回交内核

原因通常包括：

- 不希望在用户态完整接管所有协议
- 某些协议天然更适合保留在内核网络栈中处理
- 项目目标是“媒体面托管”，不是“完整用户态网络协议栈重写”
- 保留混合架构可以降低系统改造范围

因此，非 UDP、非目标业务流量通常通过 KNI 回交内核。

## 5. 关键组成部分

### 5.1 用户态业务进程

这是主业务实体，负责：

- 初始化 DPDK EAL
- 配置 port / queue
- 收取媒体面报文
- 解析 L2/L3/L4 头部
- 识别网元/节点类型
- 执行重写与转发

### 5.2 `igb_uio` / `uio`

它们在旧模式中负责：

- 将设备绑定给用户态 DPDK 使用
- 为 DPDK PMD 提供设备访问路径

### 5.3 `rte_kni.ko`

KNI 的作用是：

- 在用户态 fast path 与 Linux 内核网络栈之间提供桥接能力
- 把不在 DPDK 托管范围内的流量交回内核
- 支持控制面/非托管协议继续使用内核协议栈

## 6. 典型处理流程

### 6.1 托管流量（UDP）

1. PMD 从绑定后的 NIC 收包
2. 用户态媒体面进程解析 Ethernet / ARP / IPv4 / UDP
3. 判断是否为目标网元或目标业务流
4. 对 MAC / ARP / IP / UDP 做必要重写
5. 转发至下游节点

### 6.2 非托管流量

1. PMD 收到非 UDP 或非目标协议流量
2. 用户态逻辑判定不继续在媒体面托管
3. 通过 KNI 接口将流量送回内核
4. 后续由 Linux 内核协议栈继续处理

## 7. 旧模式的优点

- 与当时的业务边界贴合：只托管媒体面
- 对特定协议（如 UDP）性能收益明显
- 保留内核协议栈处理非目标协议，降低一次性重构难度
- 在运营商网元、虚拟化和混合网络功能场景中比较实用

## 8. 旧模式的局限

- 依赖 `igb_uio/uio` 和 `rte_kni.ko` 等配套模块
- 环境构建和内核版本适配更复杂
- 用户态与内核态之间存在额外桥接路径
- 不利于向现代 `rte_flow` / representor / transfer / SmartNIC / DPU 架构直接演进
- KNI 属于旧时代常见方案，现代项目通常不再优先选择它作为主线方案

## 9. 这段经验在当前项目里的价值

虽然当前项目不再实现这套运行时模式，但这段经验仍然非常重要，因为它体现了：

- 你真实做过 DPDK 在生产业务中的集成
- 你理解控制面/媒体面拆分
- 你理解用户态 fast path 与内核网络栈协同
- 你做过特定协议托管与报文重写转发
- 你可以把历史经验迁移到现代 DPDK 数据面平台设计中

## 10. 当前项目如何使用这段经验

在 `dpdk-dataplane-platform` 中，这段经验主要映射为：

- Phase 1 的 ARP / IPv4 / UDP 解析与重写设计
- 媒体面只关注关键流量的 pipeline 思想
- 控制面与数据面边界意识
- 后续从软件路径走向 `rte_flow` / representor / transfer 的演进思路

也就是说：

**旧模式不再作为当前代码主线实现，但它仍然是当前项目架构设计的重要经验来源。**
