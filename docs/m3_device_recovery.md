# M3 正式设备事件与主动复位

本轮将设备事件、旧句柄隔离、拓扑重发现和完整端口组主动复位接入正式 daemon。
生产路径调用实际 DPDK stop/reset/configure/queue/start，不调用独立模拟复位接口。
当前两台机器没有可验收的 SmartNIC；测试夹具只证明控制顺序和失败处理，不能代替实机报告。

## 非预期设备事件

正式启动在快照重放前登记 DPDK 21.11 已有的 INTR_RESET、INTR_RMV、DESTROY。
回调只发布原子事件序号、配置端口位图和收发门禁，不在回调里停止网卡或删除规则。
INTR_RESET 不证明旧 flow 或 indirect 句柄已清除，不能把它当成模拟器的原子复位通知。

worker 在每次 RX、TX 和 ND 发送前检查门禁；已经收到但不能继续处理的 mbuf 会归还。
主线程优先处理设备事件，停止并等待所有 worker，再保留受限管理诊断。
每次管理请求、每次后端驱动调用、创建前日志同步之后也重新检查事件，避免同一轮请求继续使用旧句柄。
驱动探测缓存同样受门禁约束，不能用旧的支持结果绕过隔离。

未知旧句柄进入 quarantine，规则、共享对象和预留引用均保留。
validate/create/query/remove、共享创建/查询/销毁、fini 和 reconcile 都不再调用 PMD。
只读身份、账本、安装记录和恢复状态仍可查询；对象数量表示最后保留的仓库记录，
不能证明复位之后网卡上还有同样数量的实际对象。

主动探测发现端口失效时，也发布同样的事件证据。RMV/DESTROY 在本进程中不能清除；
端口编号被新设备复用时，终结清理不会只凭编号 stop/close 新设备，无法确认释放安全就保留缓冲池。
事件序号饱和、回调在途或注销失败都保持保守失败，不通过清零状态解除门禁。

## 主动复位顺序

管理协议 v27 增加：

```sh
./build/dppctl --socket /path/to/ctl.sock device-status
./build/dppctl --socket /path/to/ctl.sock device-reset EXPECTED_SEQUENCE
```

EXPECTED_SEQUENCE 必须来自当前设备状态，初始值零合法，不接受 any 或保留最大值。
复位范围是 daemon 的**完整配置端口组**，不是只复位一条规则的安装口。
`device-status` 的 `device-ports count=... ids=...` 列出完整范围，位图均按这个配置顺序解释。
参数或前置证据拒绝不改变运行状态；进入流程后的错误和阶段进度保存在设备状态中。

1. 立即只读检查 IPv4/IPv6 各表默认路由、多路径及 SSH 本地地址，定位管理接口和实际 PCI parent
2. 将全部配置端口与管理 PCI parent 比较，同 PF 下的 VF/representor 也不能绕过保护，未知或读取不完整就拒绝
3. 核对已保存的设备名、固件、MAC、队列、描述符和缓冲池证据，再发现到临时拓扑核对身份
4. 捕获内存中的完整期望规则和共享定义，封住普通写入，暂停收发并等待全部 worker 退出
5. 只在旧句柄仍确定有效时删除本进程规则，再销毁共享对象；不改规则账本、版本或快照
6. 全部 stop 成功后才开始任何 reset，之后重新核对实际身份和能力，沿用原队列、RSS、offload 与缓冲池
7. 先配置完整组的队列，再启动完整组，核对链路、临时拓扑和稳定事件序号后才发布拓扑
8. 只解除确实为空的后端隔离，先恢复共享对象，再恢复原精确版本规则，随后解除收发门禁并启动 worker
9. 等待全部 worker 实际就绪，最后释放恢复计划并发布 READY

DPDK 21.11 的 reset 内部可能忽略 stop 错误，因此本项目单独检查每一个 stop 返回值。
reset 调用期间可以记录新的稳定 RESET 事件；移除、销毁、在途回调和其他阶段的新事件均阻止继续恢复。
reset 返回成功也不等于队列已经配置，或物理链路已恢复。本实现分别验证这两项，
链路和 worker 就绪各有两秒等待上限；PMD 自身阻塞不由这些等待上限保证。

## 身份、版本与失败语义

拓扑始终先发现到临时对象，再按配置端口集合核对设备名/BDF、驱动、接口编号、
角色和来源、controller/PF/VF/SF 身份、交换域和交换端口。
结构体填充、数组顺序和无效标志对应的残留数字不是身份，缺失信息也不能猜补。
发现失败、集合变化或同编号换设备都不会发布半份 live topology。

规则与共享 generation、仓库修订号以及原快照内容、inode 和修改时间保持不变。
实际对象由新句柄重新创建，COUNT 从零开始，AGE 重新计时；这与保留旧累计值含义不同。
共享对象创建或某条规则重建失败时补偿已知新对象，补偿失败保留新句柄及引用。
worker 启动失败也保留计划，不能在业务尚未就绪时宣称恢复成功。

已知对象清理失败、规则重建失败或 worker 启动失败，在身份与端口状态仍满足前提时可以用新的精确观察重试。
**PMD 的 stop/reset/configure/start 失败可能已经改变部分设备状态**，不保证原地重试可行，
也不能假设失败无副作用继续启动 worker。阶段和各口完成位图会保留供外部处置。
PMD 不提供 reset 时如实失败，不静默调用模拟器或假装已经执行硬件复位。

非预期 reset 后若仍有未知旧句柄，没有可移植的跨 PMD 方式证明它们已消失。
本实现不会再 destroy、盲目 reset 或遗忘这些指针以恢复 READY。
应先按实际设备流程完成外部清理，再使用恢复日志的精确外部确认和干净重启重放。
该边界与 [共享 COUNT 恢复保护](m3_shared_recovery.md) 一致，确认命令本身不执行设备清理。

首期正式复位仅支持独立硬件规则组，不同时迁移软件、三层、连接跟踪或 ND 状态。
这些组合在停止设备和清理对象前拒绝，原有 M2 功能仍按正常启动与回归路径运行。
管理口保护只证明当前观察窗口的接口和 PCI parent，不能证明板卡级复位不影响同板其他功能；
设备实际复位范围、固件行为、外部对象与热插拔连续性仍须实机验收。

## 验收入口

```sh
python3 scripts/verify_m3.py --build-dir build
```

单测覆盖真实生产函数体的事件门禁、mbuf 归还、后端全入口隔离、拓扑失败不发布、
管理口保护、全组 stop/reset/队列/start 顺序、第二口失败、身份和固件变化，以及正式协调器的补偿与重试。
模拟 PMD 成功的夹具只证明调用契约，不能计为设备支持或实机复位结果。
