# 业务与监护握手

`dppd --recovery-monitor SESSION_PATH` 把业务安装与独立监护关联起来。启动时核对完整
TAP 端口集合、系统与网络命名空间身份、恢复文件及其起始修订号；监护按时回复本次
随机校验请求后，业务才持久保存会话编号并继续初始化。默认不启用该选项。

## 启动顺序

使用预先创建且由当前部署管理的持久 TAP，存储目录须已存在。先启动监护：

```sh
sudo ./build/dppd-monitor run /var/lib/dppd/hardware.recovery \
  /var/lib/dppd/rules.state /var/lib/dppd/monitor-session-001 \
  0:dppdtap0 1:dppdtap1
```

看到 `monitor ready` 后，用相同有效用户启动业务，CPU 编号按实际环境调整：

```sh
sudo ./build/dppd -l 0-1 --no-huge --no-pci -m 64 --no-telemetry \
  --vdev=net_tap0,iface=dppdtap0 --vdev=net_tap1,iface=dppdtap1 -- \
  --ports 0,1 --mbufs 8191 --cache 0 \
  --state-path /var/lib/dppd/rules.state \
  --recovery-path /var/lib/dppd/hardware.recovery \
  --recovery-monitor /var/lib/dppd/monitor-session-001
```

原生标识仍需适配后的驱动与 `--tap-owner-cookie`，见 [TAP 原生标识](tap_owner_cookie.md)。
普通 TAP 同样支持握手，但不会因此获得原生规则标识。当前只接受完整的本地 TAP 端口
集合，不接受混合物理端口或缺少端口的会话。

握手位于 EAL 探测之后、本项目配置队列和重放快照之前。EAL 与 PMD 的设备探测已经
发生，因此拒绝启动不表示整个驱动初始化完全没有副作用。

## 一次安装如何检查

1. 重新读取目标 TAP 身份，与绑定端口比较，并向监护请求新回复
2. 保存端口与安装意图，读取创建前的内核规则线索
3. 即将进入驱动前再次请求回复，避免复用写盘和查询之前的结果
4. 保存实际创建结果后再次检查，失效时让事务使用真实 handle 回滚

回复前，监护检查恢复文件仍指向原文件，并排空已经到达的接口事件。接口删除、改名、
事件丢失等会保存失效终态，不再回复成功。正常链路变化和 TC 写入仍按
[生命周期监护](recovery_monitor.md) 处理。

握手或身份检查失败在当前业务进程内锁存，后续成功也不自动恢复安装。启动 worker
前和主循环中同样检查监护，故障后停止 worker、关闭管理入口并以失败状态退出。
删除当前进程已持有 handle 的规则不依赖监护，避免监护退出反而阻止必要清理。

全部已知规则确实删除成功后，原机制可以记录 clean。若只有已保存的安装意图、没有
可核对的创建结果，或删除/写盘失败，仍保留待核对状态。测试在意图写入前暂停业务、
结束监护后恢复执行，最后一次检查阻止进入驱动，已经落盘的 intent 仍按此规则保留。

## 新鲜回复的边界

每次 IPC 往返使用新的 16 字节随机数，共用一个单调时钟截止时间，预算 **1000 ms**。
超时、短消息、过长消息、未知版本、会话或随机数不符均拒绝。这约束 IPC 往返，不是
文件 I/O 或驱动调用的统一超时。即使暂停的监护仍持有文件锁，也不能通过新请求。

通道采用 Linux 抽象 Unix `SOCK_SEQPACKET` socket，地址由会话编号派生，退出后不留
磁盘 socket 文件。两端核对内核连接凭据，只接受相同有效用户；业务还核对对端 PID。
会话文件须是该用户的私有、单链接普通文件，业务保留原描述符，不能用同内容的新文件
冒充旧会话。抽象地址不使用文件权限保护，关闭和凭据语义见
[Linux Unix socket 手册](https://man7.org/linux/man-pages/man7/unix.7.html)。

固定 64 字节小端消息布局：

| 偏移 | 内容 |
| --- | --- |
| 0–7 | `DPPMIPC1` |
| 8–15 | 请求类型 1 与四字节保留零字段 |
| 16–31 | 会话编号 |
| 32–47 | 本次随机数 |
| 48–63 | 绑定恢复文件的设备号与 inode |

检查成功才原样回复。服务端最多保留八个待处理连接，非阻塞收发并到期关闭；坏消息
只关闭其连接。槽位占满时继续检查已有连接和接口事件，避免监听队列反复唤醒空转。
该通道不提供独占写入权，也不是抗管理员篡改的认证机制。

`dppd-monitor show` 继续只读磁盘，仍为 `freshness=unverified`。业务握手成功不使离线
文件成为以后任意时刻的活性证明；`dppd-recovery plan` 也不因此获得删除许可。

## 恢复记录 v6 与重启

普通部署继续创建 v5 文件。仅显式握手成功后，干净恢复记录才升级为 **v6**：长度仍为
54336 字节，沿用 v5 端口和安装记录，在元数据原保留区的绝对偏移 **9264–9279** 保存
会话编号，增加 revision 并同步成功后才继续。待核对的 v6 端口记录必须有非零会话编号，
损坏组合拒绝读取。`show` 新增 `monitor-required=yes session=... freshness=unverified executable=no`。

原生 cookie、预期内容与安装/删除结果仍分别保存，监护编号不能代替它们。完整清理
清除当前会话编号，但保留格式 v6，后续启动仍须配置监护，不能通过省略选项回退。
新程序兼容 v1–v6；不认识 v6 的旧程序拒绝文件，不会当作普通干净记录继续使用。

每次新业务进程都需要新会话。正常退出后，旧监护的起始 revision 已落后，不能再次
绑定。确认恢复记录 clean 后结束旧监护，用新会话文件名启动监护，再启动业务重放。
旧会话文件保留作诊断；待核对活动先按原恢复流程处理，不能补开监护来补猜历史。
在端口与安装意图写入前就退出的业务尚无已记录硬件活动，但它的旧绑定起点仍不能复用。

## 后续边界

本阶段完成业务启动绑定、安装前后检查和活性故障退出。回复之后的调度间隔、驱动
调用和其他程序的 TC 写入仍未原子隔离，重复检查不能消除这些间隔。新鲜回复只表示
对应请求得到响应，不保证未来一直有效。

下一步限定受控网络命名空间与允许写入者，建立业务退出后向恢复操作交接写入权的
流程，再把会话证据接入清理计划。当前没有跨进程自动删除命令，也不把会话编号当作
连续历史的完整证明。

## 验证

2026-10-11，两套 DPDK 21.11.9 构建完成 `-Werror` 编译和 **34/34 单测**。握手、恢复
保护、会话证据、事件监视和逐次记录五项通过 AddressSanitizer/UBSan。覆盖真实子进程
超时、随机数与会话错配、消息边界、坏请求、慢连接释放、凭据、错误锁存、绑定同步
失败及 v6 重新打开后的强制监护语义。

```sh
sudo python3 tests/integration/monitor_handshake.py --build-dir build
sudo python3 tests/integration/monitor_handshake.py --build-dir build-native --native
```

每种构建验证 12 个真实 TAP 场景：正常安装与新会话重放、业务崩溃后保留绑定、端口映射错配、集合缺失、
恢复文件错配、启动时监护暂停、运行中监护退出/暂停、会话文件替换，以及安装意图前、
驱动创建前和实际创建后的失效窗口。核对进程退出、真实规则、恢复记录和业务快照。
故障包装只在独立测试入口中使用；测试仅创建并按索引核对后清理自己的持久 TAP。

崩溃后的链路通知可能延迟到达。测试要求变化中的查询窗口返回拒绝、候选数为零，
稳定后重新查询才检查候选，过程中恢复文件与快照必须始终不变。未绑定业务的独立
监护、旧 TAP 恢复保护、原生标识/内容与八个查询窗口场景一并回归通过。
