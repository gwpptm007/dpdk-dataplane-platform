# M3 通用 PCI 与接口身份采集

本功能把“这是哪一个 Linux 接口”与“它是不是 uplink、PF、VF 或 SF”分开处理。
非 mlx5 PCI PMD 现在也可以形成经过核对的接口身份，角色仍保持 UNKNOWN。
管理协议继续使用 v27，结构和消息大小不变。

## 什么信息可以相信

`device_name` 和 `if_index` 保留 PMD 报告的设备名与接口编号。
它们说明驱动给出了什么观察，单独出现并不证明当前网络命名空间中有对应接口。
[DPDK 21.11 的定义](https://doc.dpdk.org/api-21.11/structrte__eth__dev__info.html)
允许 `if_index` 为零，表示没有绑定的宿主接口。

正式 `discover` 只有在完整核对通过后才填写 `interface_name`，同时发布已经核对的 `phys_port_name`。
基础核对失败时，这两个字段均为空，`role_error` 保存具体错误。
读取器已经返回了完整字符串，也不能在其最终返回失败时把这些字符串当作可信身份。

基础核对成功和角色解析成功是两回事：

| 观察结果 | 接口字段 | 角色与来源 | `role_error` |
| --- | --- | --- | --- |
| 通用 PCI 核对成功 | 保留可信接口与可选物理名称 | UNKNOWN / UNKNOWN | `-ENOTSUP` |
| mlx5 基础核对成功且名称符合原有规则 | 保留可信接口与物理名称 | 原有可信角色 / mlx5 来源 | `0` |
| mlx5 基础核对成功但没有物理名称 | 保留可信接口，物理名称为空 | UNKNOWN / UNKNOWN | `-ENODATA` |
| mlx5 名称语法或 representor 标志矛盾 | 保留已经核对的基础身份 | UNKNOWN / UNKNOWN | 解析错误 |
| 基础身份读取或比较失败 | 接口名与物理名称都为空 | UNKNOWN / UNKNOWN | 具体读取或比较错误 |

因此，不能仅凭 `role_error=-ENOTSUP` 判断基础身份成功。
没有新增独立的 verified 字段；这里的可信字段语义只适用于正式发现路径。
自行构造结构体或调用纯名称解析器，仍须由调用方证明输入来源，不能把测试数据当成内核观察。

## 核对顺序

1. 仅处理规范 PCI BDF 和非零、可表示为 Linux 接口编号的 `if_index`
2. 在当前网络命名空间发送 `RTM_GETLINK`，取得完整接口名和可选物理端口名
3. 核对 `/sys/class/net/接口名/ifindex` 与 PMD 编号完全相同
4. 解析该接口的 `device` 路径，核对真实路径最后一项与 PMD PCI BDF 完全相同
5. 核对可选 `phys_port_name`，不能把一边存在、一边缺失或值不一致当作成功
6. 再读一次当前网络命名空间中的接口名和物理名称，并核对 `if_nametoindex`
7. 全部成功后才发布接口字段，再按驱动决定是否进行角色解析

PCI 或接口编号错误不会因为物理端口名缺失而被跳过。
第二次读取发现改名、名称出现或消失、编号复用时，保留失败结果，不发布半份身份。
重新发现仍先写临时拓扑，全部端口身份一致后才发布；失败保持原输出的全部字节。

所有字符串都有固定读取上限，超长、半截、内嵌 NUL、重复关键 netlink 属性及异常发送地址都会拒绝。
sysfs 的短读会继续读取；已经读到一部分内容后又报缺失或不支持，按读取不完整拒绝。
权限错误、PCI 路径错误和接口编号错误不会变成“这个驱动不支持角色”而被吞掉。

## 物理端口名是可选证据

通用 PCI 接口不一定提供 `phys_port_name`。
Linux 在不支持该属性时，可以省略 netlink 属性，并让 sysfs 读取返回不支持。
相关路径见 Linux 的
[netlink 物理名称填充](https://github.com/torvalds/linux/blob/v5.15/net/core/rtnetlink.c#L1091)
和 [sysfs 物理名称读取](https://github.com/torvalds/linux/blob/v5.15/net/core/net-sysfs.c#L465)。

本实现允许两边都没有名称。sysfs 文件不存在、属性不支持或没有有效内容时按空值参与比较；
只有 netlink 也为空且其他身份核对全部通过，才能继续。
一侧有名称、两侧内容不同、第二次 netlink 名称变化、权限错误或内容损坏都会拒绝。
“没有有效内容”不包括内嵌 NUL 等格式错误，也不包括读到半份内容后才失败。

即使非 mlx5 的物理名称碰巧是 `c0pf0vf1`，也只保存这个经过核对的名称，不赋予 VF 角色。
mlx5 继续沿用严格的名称与 representor 标志契约，不增加供应商猜测或编号推断。

## 对 transfer 的影响

`pair` 不要求 PF/VF/SF 角色，可以使用 UNKNOWN 端点，但仍须满足原有同交换域、
端点存在、交换端口不别名、安装口和版本等要求，并通过真实 PMD 校验。
有了可信 Linux 接口，并不自动意味着这个端点支持 transfer。

六个命名模板仍要求源和目的角色都有原有可信证据。
它们不会因为通用接口身份成功、representor 标志存在或物理名称类似 mlx5 而放行。
安装口的角色要求没有新增，仍沿用原有规划器的安装口和交换域检查。

## 当前边界与测试

没有宿主接口的 VFIO 端口、`if_index=0`、非规范 PCI 名称和 auxiliary SF 设备名仍不补猜。
同一 PCI 下存在多个接口时，也不会遍历目录挑选一个接口填空；必须使用 PMD 明确报告的非零编号核对。
接口名目前接受字母、数字、下划线、短横线和点，其他命名保守拒绝。

多次只读观察不是硬件原子快照，也不能证明热插拔期间的设备实例连续性。
实际硬件安装、复位、外部对象归属和管理接口保护仍须各自核对。
本功能不修改内核接口、路由、网络命名空间、设备绑定或网卡状态。

针对性验证使用独立 scratch 目录和包装后的 PMD/netlink/sysfs 输入。
`test_topology`、`test_transfer` 与 `test_transfer_management` 的普通严格构建和 ASan/UBSan 均通过，
覆盖双边缺名、单边缺名、PCI/编号错误、权限失败、读取中途失败、名称变化、失败不发布、
通用 UNKNOWN `pair` 与六模板拒绝，以及版本、COUNT 和快照不受拒绝请求影响。
这些结果是软件契约验证，不是非 mlx5 实机 transfer 或硬件恢复验收。
